# 重建轻量新人训练运营系统

> 状态：Draft v0.9（产品方案完整，待确认生产数据与切换方式）  
> 类型：产品重建 PRD  
> 风险等级：P1（新产品主线、训练数据、正式达标决定与新旧切换）  
> 主要用户：培训负责人、新人学员  
> 设计依据：`DESING.md`、`CONTEXT.md`、新人训练相关 Accepted ADR

## Executive Summary

本产品不是 PPT 练习工具、通用学习平台或 AI 聊天产品，而是一套面向持续招聘企业的新人训练运营系统。它同时服务两种节奏：每年 3 月、7 月的大批校招训练，以及全年少量社招滚动入训。

产品通过复用已发布训练方案、批量分配学员、自动完成确定性判分和录音初评、把异常分流给培训负责人、集中完成人工达标确认，使固定培训团队能够承载更多新人。第一版成功与否不看学员毕业后的日活，而看单位培训人力、达标周期和质量护栏是否改善。

重建采用“新业务核心独立、旧系统可回退、基础设施窄复用”的方式。MVP 只包含训练方案、训练班、学员执行、评测补练、异常处理、人工达标和结班度量，不迁移当前平台的大量通用治理和 AI 配置能力。

## Product Decision

**建议重新开发，但不是把当前项目换一种目录结构重写一遍。** 本次重建的对象是产品边界、业务模型和主流程；身份认证、对象存储、消息通道、AI Provider 接入等成熟基础设施只有在边界清楚且验证可复用时，才通过窄接口接入。

推荐决策如下：

| 决策项 | 推荐选择 | 原因 |
|---|---|---|
| 产品边界 | 只做新人基础训练运营 | 直接对应持续招聘和培训降本目标 |
| 主要运营对象 | 训练方案、训练班、入训记录 | 用业务对象代替功能模块拼盘 |
| 训练任务 | `learn \| quiz \| record` | 覆盖当前必要训练，联合类型可穷举 |
| AI 定位 | Record 后台初评能力 | 保留语言判断价值，不制造 AI 产品中心 |
| 人工介入 | 异常分流 + 正式达标复核 | 把培训人力用在高价值判断上 |
| 新旧关系 | 单向迁移、禁止长期双写 | 保持可回退，同时避免两套权威 |
| 技术策略 | 新业务核心独立，基础设施窄复用 | 防止旧复杂度重新渗入 |
| 成功标准 | 人时、周期、质量护栏 | 不用低频产品的 DAU 误判价值 |

## Goal

从当前功能和治理范围过宽的销售训练平台中，重新建立一个直接、清晰、简单的新人训练运营产品。它面向持续招聘企业，以每年 3 月、7 月校招高峰和全年零星社招为主要节奏，通过标准化训练、自动评测、针对性补练、异常分流和人工达标复核，降低每名达标新人的培训人员工时并缩短达标周期，同时守住训练质量。

## Product Promise

> 培训负责人用一套可复用的训练方案启动校招班或滚动社招班；新人自主完成学习、答题和录音任务；系统自动处理常规评测与补练，只把真正需要判断的异常送给培训负责人，并最终形成可解释、可审计的基础训练达标决定。

## Problem Statement

### 当前业务问题

- 校招高峰时，大量新人会在短时间集中入训，培训团队容易重复讲解、批改、催办和整理结果。
- 零星社招人数少，但若每次重新组织一套班级和培训动作，单位成本反而更高。
- PPT 讲解、Demo 讲解、小测和录音评分本身只是训练手段；若不能形成批量运营、异常分流和成本度量，功能再多也无法证明降本提速。
- 当前项目把新人训练扩展成了内容、题库、AI Coach、角色、实时对练、知识库、配置治理和多套发布体系的集合，培训负责人需要理解过多系统概念。
- 当前北极星“形成达标档案”描述了产物，但没有直接证明减少了多少人工或缩短了多少时间。

### 根因

- 产品边界按功能和技术能力扩张，而不是围绕培训负责人完成一次训练交付组织。
- AI 被建模为多个显性产品模块，而不是藏在评测和反馈流程中的能力。
- 管理端强调配置完整性，弱化了批次是否按期推进、谁需要介入和培训负载是否超标。
- 新旧业务权威、修订、发布和迁移规则不断叠加，导致实现和认知成本上升。

### 产品机会

把产品收敛为“训练方案复用 + 双节奏开班 + 学员自助执行 + 自动评测补练 + 异常人工处理 + 达标与成本复盘”这一条完整主线。以组织级重复使用替代对单个学员长期留存的错误追求。

## Target Users and Jobs To Be Done

### 培训负责人（MVP 主用户）

**场景**：校招高峰前准备训练，训练期间监控进度、处理异常，结束后确认达标并复盘成本；平时持续接收零星社招。

**核心任务**：

- 复用或调整一份训练方案并发布版本；
- 创建定期训练班或滚动训练班；
- 在班级上下文内导入、快速新建、去重并分配学员；
- 判断当前批次能否按期完成，以及谁正在阻塞；
- 只处理低置信度、红线、反复未通过、技术失败和待达标确认等例外；
- 记录正式达标、补练、补证据或暂缓决定；
- 对比培训人员工时、达标周期和质量结果。

**离开产品前的可验证结果**：知道当前最重要的待办已经处理，训练状态和正式决定已保存并可审计。

### 新人学员

**场景**：在规定培训周期内自主完成公司、产品和销售基础训练。

**核心任务**：

- 立即知道当前要做什么、为什么做、如何通过；
- 阅读指定材料、完成小测、提交 PPT/Demo/场景表达录音；
- 获得结构化、可执行的反馈；
- 未通过时知道需要补什么、何时可以重新提交；
- 结果处理中可以离开，之后从同一位置恢复。

**离开产品前的可验证结果**：当前任务已可靠保存，下一步和截止时间明确。

### 平台管理员（支持角色，不是产品主线）

负责账号、组织、基础权限、Provider 和运行健康。MVP 不为其建立新人训练内部的通用配置中心；相关能力通过现有平台或部署配置提供。

## Operating Cadence

### 定期训练班 `scheduled`

- 适用于 3 月、7 月校招高峰；
- 有统一开始时间、截止时间、负责人和训练方案版本；
- 支持批量导入、统一提醒、批次进度、风险排序、批量复核和结班；
- 重点优化峰值吞吐、异常队列和培训负责人负载。

### 滚动训练班 `rolling`

- 适用于全年零星社招；
- 班级长期有效，每名学员按加入时间计算个人截止时间；
- 复用同一已发布训练方案，不要求每几名社招重新创建班级；
- 仅当训练方案发生正式变化时，新加入学员绑定新版本；已加入学员不自动迁移。

## Product Principles

1. **培训运营优先于训练功能数量**：先减少人工步骤，再增加训练形式。
2. **异常驱动人工**：常规项自动通过规则处理，人工注意力集中在需要判断的对象。
3. **一名学员一条下一步**：学员端不展示模块菜单、系统配置或竞争入口。
4. **AI 隐藏在结果里**：界面展示评测、证据和建议，不建立独立“AI 中心”。
5. **正式决定始终可追溯**：AI 初评与人工决定分开保存，不能互相覆盖。
6. **发布即冻结**：班级绑定确切训练方案版本，后续修改只影响新学员。
7. **上下文内完成**：学员、材料、题目和评分标准缺失时，在当前班级或方案中选择或快速新建。
8. **不以兼容旧模型为目标**：只迁移有业务价值的数据，不复制旧接口和抽象。

## Success Metrics

### 北极星指标（待业务基线确认）

**每名基础训练达标新人的培训人员工时**

```text
统计周期内培训人员直接投入新人训练的总分钟数
÷ 同期形成有效“基础训练达标”决定的新人数
```

直接投入包括人工讲解、人工批改、催办、异常处理、补练指导和达标复核；不包含一次性产品研发投入。首个试点通过抽样工时记录与系统事件共同建立口径，不能仅用页面停留时间推算。

### 结果指标

| 指标 | 定义 | 目的 |
|---|---|---|
| 入职到达标周期 | Enrollment 生效到有效达标决定的中位时长 | 验证是否提速 |
| 按期达标率 | 截止时间前达标人数 / 应完成人数 | 判断班级是否按计划交付 |
| 培训负责人承载量 | 同期活跃新人 / 实际培训负责人 | 验证规模杠杆 |
| 人工介入率 | 需要人工处理的学员或评测 / 全部学员或评测 | 判断自动化是否有效 |
| 补练率 | 进入 remediation 的学员 / 已提交学员 | 识别训练难度与内容问题 |

### 质量护栏

| 指标 | 不允许发生的情况 |
|---|---|
| AI 初评人工推翻率 | 为降本而放宽自动评测，导致人工频繁推翻 |
| 抽检不合格率 | 批量确认后抽检发现基础能力并未达标 |
| 红线漏检率 | 事实错误、虚假承诺、敏感信息等红线未进入人工 |
| 评测低置信度率 | Provider 或材料质量问题被伪装成正常通过 |
| 申诉成立率 | 学员合理申诉揭示评测或流程系统性错误 |

所有目标值必须在获得当前人工培训基线后设定；本 PRD 不发明峰值人数、降本比例或达标时限。

## MVP Scope and Release Boundary

### MVP 必须形成的完整闭环

1. 培训负责人创建或复制训练方案，配置 `learn`、`quiz`、`record` 并发布不可变版本；
2. 创建 3/7 月定期班或全年滚动班，在班级中完成学员导入、去重和分配；
3. 学员通过单一入口完成当前任务，提交可恢复、结果可解释；
4. 系统确定性判分 Quiz，异步初评 Record，并把异常可靠分流；
5. 培训负责人处理异常、要求补练或补证据，并记录正式达标决定；
6. 结班时能够回答用了多少培训人力、多久达标、质量是否守住。

缺少以上任一环节，都不能称为 MVP 完成。特别是只有“讲 PPT / 讲 Demo + AI 打分”不构成产品闭环。

### MVP 能力边界

| 领域 | MVP 包含 | MVP 不包含 |
|---|---|---|
| 方案 | 草稿、复制、校验、预览、发布版本、历史只读 | 通用内容市场、任意工作流、跨领域资源发布 |
| 班级 | 定期班、滚动班、启动、暂停、关闭、取消 | 复杂排课、线下教室、讲师结算 |
| 人员 | 搜索、快速新建、CSV 导入、去重、批量分配 | 完整 HR 主数据管理、组织架构维护 |
| 学习 | 材料学习确认、当前位置恢复 | SCORM/xAPI、视频防刷、学习时长监控 |
| 测验 | 单选、多选、判断、确定性判分 | 主观题、AI 出题、通用题库运营 |
| 表达 | 录音、上传、转写、结构化初评、补练 | 实时语音对练、数字人、开放聊天 |
| 运营 | 进度、风险、待办、提醒、复核、结班数据 | 通用 BI、自助报表搭建、排行榜 |
| 治理 | 业务权限、审计、留存策略、运行健康 | 培训负责人可见的模型/Prompt/Provider 配置中心 |

### 后续版本进入条件

任何新能力只有同时满足下列条件才进入路线图：

- 在至少两个真实训练批次中重复出现；
- 能明确减少培训人员工时、缩短达标周期或降低质量风险；
- 无法通过现有任务类型、规则、搜索或人工流程解决；
- 有明确业务负责人、数据口径和退出条件；
- 不要求重新引入通用 Agent、Persona、RAG 或任意工作流作为前置平台。

## Baseline and Target-Setting Plan

上线前先用一轮当前人工培训建立基线，避免用想象中的降本目标验收产品。

| 要采集的基线 | 采集方式 | 负责人 | 结果用途 |
|---|---|---|---|

| 集中提交峰值 | 训练日程和历史记录 | 产品/技术 | 上传与评测队列压测 |

| 批改、催办、异常处理时间 | 按动作分类抽样登记 | 培训负责人 | 判断自动化价值 |

## Domain Language and Object Model

普通用户界面使用中文业务词，不展示数据库 ID、原始枚举、Prompt、模型参数、traceId 或内部任务类型。

| 业务词 | 技术名 | 定义 | 不使用的旧表达 |
|---|---|---|---|
| 训练方案 | `TrainingProgram` | 可持续维护的一套新人训练定义 | 路径编排、模块集合、训练模板中心 |
| 方案版本 | `ProgramVersion` | 发布后不可修改、可被训练班冻结绑定的完整快照 | working/published 资源联合、ReleasePlan closure |
| 训练班 | `Cohort` | 一组按相同运营节奏接受训练的新人 | 队列、销售训练队列 |
| 入训记录 | `Enrollment` | 某位新人进入某训练班并绑定确切方案版本的记录 | 学员路径实例 |
| 训练任务 | `TrainingTask` | 学员必须完成的学习、答题或录音动作 | ActivityDefinition、模块 |
| 训练提交 | `Submission` | 学员对训练任务提交的不可变答案或录音证据 | 通用 Attempt 信封 |
| 评测结果 | `Evaluation` | 确定性或 AI 评测产生的结构化初评、证据与置信度 | AI 洞察、模型结论 |
| 达标决定 | `ReviewDecision` | 有权限培训负责人对新人作出的正式决定 | AI 达标、自动准入 |
| 评测任务 | `AssessmentJob` | 后台执行转写、评分和结果落库的持久任务 | 前端 loading、进程内 BackgroundTask |

### 对象关系

```text
TrainingProgram
  └─ ProgramVersion（不可变）
       └─ ordered TrainingTask[]

Cohort ──binds──> ProgramVersion
  └─ Enrollment
       ├─ Submission[]
       │    └─ Evaluation[]
       └─ ReviewDecision[]
```

### 第一版训练任务联合

#### `learn`

- 绑定一个已上传材料或结构化学习内容；
- 展示目标、预计时间和完成条件；
- 完成条件仅支持“明确确认完成”或“完成指定内容”，不跟踪虚假阅读时长；
- 不使用 AI。

#### `quiz`

- 支持单选、多选和判断；
- 客观题使用确定性规则判分；
- 冻结题目、答案、分值、通过线和允许次数；
- MVP 不包含 AI 出题、简答题和通用题库工作台。

#### `record`

- 支持 PPT 讲解、Demo 讲解和异步场景表达；
- 绑定任务说明、参考材料、时间限制、评分维度、关键事实和红线；
- 保存原始录音，异步完成校验、转写和评分；
- AI 只产生初评、证据、置信度和改进建议；
- 低置信度、红线、处理失败或多次未通过进入人工队列。

## Lifecycle and State Model

### TrainingProgram

```text
draft → published
           └→ superseded
```

- 草稿可编辑；
- 发布生成新的不可变 ProgramVersion；
- 旧版本可停止用于新班，但不能修改或删除活跃/历史引用。

### Cohort

```text
draft → active → closed
          ├→ paused → active
          └→ cancelled
```

- 只有 draft 可以改变模式、方案版本和批次关键日期；
- active 后新增学员必须明确影响，并绑定该班冻结版本；
- closed 后只读，重新训练通过新 Enrollment 处理。

### Enrollment

```text
assigned → training → awaiting_review → ready
                         ├→ remediation → training
                         ├→ evidence_required → training
                         └→ deferred

任意非终态 → withdrawn
```

### TrainingTaskView（由 Submission 和 Evaluation 投影）

```text
locked → available → submitted → processing → passed
                              ├→ retry
                              ├→ needs_review
                              └→ processing_failed
```

前端不得自行推断状态；所有标签、允许动作和下一步由后端 ViewModel 返回。

## Core Data Requirements

PRD 只规定业务事实与约束，不提前绑定 ORM 结构。所有核心记录必须带组织范围、创建/更新时间和审计关联。

### TrainingProgram / ProgramVersion

| 字段/事实 | 要求 |
|---|---|
| 方案身份 | 同一业务方案跨版本保持稳定身份 |
| 版本号 | 组织内对该方案单调递增，可被人理解 |
| 适用对象 | 说明校招/社招、岗位或必要前置条件，不做任意规则引擎 |
| 任务顺序 | 发布后固定，有稳定 task key |
| 内容快照 | 任务说明、材料版本、题目答案、评分表和完成规则可复现 |
| 发布信息 | 发布人、时间、校验结果、变更摘要 |
| 引用保护 | 被班级或历史记录引用的版本不能修改或物理删除 |

### Cohort / Enrollment

| 字段/事实 | 要求 |
|---|---|
| 班级模式 | `scheduled` 或 `rolling`，创建后启动前可改，启动后冻结 |
| 方案绑定 | Cohort 指向明确 ProgramVersion；Enrollment 再保存实际冻结版本 |
| 日期 | 定期班使用统一日期；滚动班由加入时间 + 周期计算个人日期 |
| 负责人 | 至少一名主负责人，可有协作负责人；动作受对象范围约束 |
| 学员唯一性 | 同一人不能在同一班重复 Enrollment；跨活跃班冲突必须预览 |
| 退出 | 不删除历史提交，记录退出时间、原因和操作者 |
| 进度 | 由冻结任务与有效提交投影，不由前端累计或手工修改 |

### Submission / Evaluation / ReviewDecision

| 字段/事实 | 要求 |
|---|---|
| Submission | 每次最终提交不可变；技术重试不能生成新的学习尝试 |
| 幂等身份 | 提交、批量分配、正式决定都有客户端/业务幂等键 |
| Evaluation | 引用 Submission、评测合同版本、输入材料版本和执行任务 |
| 多次评测 | 重评追加 Evaluation，不覆盖首次结果；标记当前有效视图 |
| 正式决定 | 只由有权限人员写入，包含决定、原因、证据范围和版本 |
| 决定变更 | 新记录引用被替代记录，原记录永久可审计 |
| 敏感内容 | 录音、转写、自由文本反馈与普通事件数据分离存储和授权 |

## Core Business Rules

### 版本与生效

1. 草稿不是训练权威；只有发布成功的 ProgramVersion 可以被班级使用。
2. 发布是“全有或全无”：任一任务不完整时不产生半个版本。
3. 已启动班级不跟随方案最新版本。滚动班需要升级时，培训负责人明确选择“仅新加入学员生效”或创建新班。
4. 若确需迁移尚未开始的 Enrollment，必须预览影响、逐项记录结果并可追溯；已产生 Submission 的学员默认不迁移。

### 完成、通过与达标

1. **任务完成**只表示产生了符合要求的有效 Submission。
2. **任务通过**表示确定性判分或有效 Evaluation 满足冻结规则。
3. **训练完成**表示所有必修任务已完成，不等同于正式达标。
4. **正式达标**只来自有效 ReviewDecision=`ready`。
5. 技术失败、Provider 失败、低置信度和材料缺失都不能计为学员未通过。

### 截止时间与逾期

1. 所有时间以组织配置时区保存和展示，服务端以明确时间戳判定。
2. `scheduled` 使用班级截止时间；`rolling` 使用 Enrollment 个人截止时间。
3. 逾期不自动删除草稿或禁止补交；是否允许补交由冻结方案规则和人工决定共同控制。
4. 暂停班级时，截止时间是否顺延必须由培训负责人预览并明确确认，禁止系统暗自推移日期。

### 重试与补练

1. 学习尝试次数由 ProgramVersion 冻结，不能在学员未通过后临时放宽且不留痕。
2. 系统技术重试不消耗学员尝试次数。
3. 达到上限后只能通过有原因的人工决定追加机会或进入其他处理状态。
4. 补练必须指向具体薄弱项、材料和重新提交条件，不生成无解释的“个性化路径”。

### 批量动作

1. 所有批量动作先预览目标数、排除项、风险和不可逆影响。
2. 单项权限或数据失败不回滚无关成功项，但必须逐项返回并可只重试失败项。
3. 批量达标不能包含红线未处理、低置信度、证据缺失或处理失败对象。
4. 批量提醒、导入和复核都需要批次级幂等和审计。

## End-to-End Product Flows

### Flow A：制作并发布训练方案

1. 培训负责人打开训练方案列表并复制现有方案或创建空白草稿。
2. 按顺序添加 `learn`、`quiz`、`record` 任务。
3. 在当前编辑页上传材料、录入题目或评分维度；系统执行去重与校验。
4. 预览学员视角和通过条件。
5. 点击“发布方案版本”。
6. 系统验证任务完整性、文件可用性、答案、评分合同和 Provider readiness。
7. 验证通过后原子生成不可变 ProgramVersion；失败时草稿和输入保留。

### Flow B：启动校招定期班

1. 培训负责人选择已发布方案，创建定期训练班并设置起止时间。
2. 在班级内上传名单或快速新建新人。
3. 系统预览新增、重复、无效和无权限项；支持下载错误报告。
4. 培训负责人确认成功项，失败项保持可修正，不重复处理成功项。
5. 启动训练班，系统创建 Enrollment 并发送入训通知。
6. 班级详情持续显示按期风险、未开始、处理中、补练和待复核对象。

### Flow C：滚动社招入训

1. 培训负责人进入常驻滚动班。
2. 搜索已有账号或快速新建最小必要资料。
3. 系统基于加入时间计算个人截止时间并绑定当前对新学员生效的 ProgramVersion。
4. 新人立即收到当前任务；无需新建微型班级或离开当前页面补资料。

### Flow D：学员完成训练

1. 学员进入“我的训练”，看到唯一当前任务、整体进度和截止时间。
2. 完成 `learn` 或 `quiz` 后，系统立即返回确定性结果和下一步。
3. 完成 `record` 时，浏览器保留录音草稿；上传成功后返回持久任务状态。
4. 学员可离开页面，评测完成后通过通知和原任务页查看结果。
5. 未通过时，结果说明证据、薄弱项、补练材料和重新提交条件。

### Flow E：异常分流与人工处理

1. 系统把处理失败、低置信度、红线、多次未通过和逾期对象加入待办队列。
2. 培训负责人先看影响和推荐动作，再查看证据和完整记录。
3. 可执行重试评测、要求重录、补充证据、人工判定或联系学员。
4. 每个动作记录对象、原因、前后状态和操作者。

### Flow F：达标复核

1. 所有必修任务满足条件后，Enrollment 进入 `awaiting_review`。
2. 系统生成复核视图，汇总任务结果、关键证据、低置信度和补练历史。
3. 低风险对象支持批量确认，但必须展示数量、抽检策略和影响。
4. 培训负责人记录 `ready`、`remediation`、`evidence_required` 或 `deferred`。
5. AI 初评保持原样，人工决定追加保存，不覆盖历史。

### Flow G：结班和复盘

1. 培训负责人确认未完成、延期和退出人员的处理结果。
2. 系统生成批次完成度、周期、补练、人工介入和质量护栏数据。
3. 对比当前批次与基线/上一个可比版本，但不把不同方案版本直接混为同一口径。
4. 关闭训练班后只读；优化内容通过创建新 ProgramVersion 完成。

## Core Page Specifications

### P1 待处理

**页面任务**：当培训负责人开始一天工作时，帮助其基于等待时间、风险和影响人数处理最重要的训练异常，并得到队列持续下降的可验证结果。

- 核心对象：异常项、待复核项、失败 AssessmentJob、逾期 Enrollment；
- 主操作：处理当前异常；
- 核心信息：原因、影响对象、等待时长、风险、已保留结果、推荐恢复动作；
- 次级操作：按班级、类型、负责人和状态筛选；
- 禁止：无行动价值 KPI、排行榜、装饰图表和 AI 洞察卡；
- 状态：加载、无待办、筛选无结果、部分数据、无权限、失败、数据过期；
- 响应式：桌面为紧凑队列 + 详情；窄屏为列表到独立详情；
- 埋点：异常进入、首次打开、处理动作、处理时长、恢复结果。

### P2 训练班列表

**页面任务**：当培训负责人管理多个批次时，帮助其比较班级状态、节奏和风险并进入需要关注的班级。

- 核心对象：Cohort；
- 主操作：创建训练班；
- 关键列：名称、模式、方案版本、开始/截止、学员数、按期风险、待处理数、状态；
- 常用筛选：进行中、定期/滚动、负责人、风险；
- 空状态：解释定期班与滚动班差异并提供创建入口；
- 大数据：服务端分页、排序和筛选，URL 保留状态。

### P3 训练班详情

**页面任务**：当培训负责人运营一个训练班时，帮助其判断是否按计划推进、谁需要介入并完成学员分配、提醒、异常处理和结班。

- 页面模式：Dashboard–Drilldown + 学员结构化列表；
- 主操作随状态变化：草稿时“启动训练班”，进行中“处理高风险学员”，收尾时“检查并关闭训练班”；
- 首屏结论：是否按计划、主要阻塞、待处理数、下一关键日期；
- 核心列表：学员、当前任务、进度、截止、风险原因、最近结果、下一步；
- 上下文内动作：导入/快速新建学员、修正失败项、发送提醒、打开复核；
- 部分成功：明确新增、重复、失败和跳过数量，可只重试失败项；
- 并发：班级版本冲突时保留输入并要求刷新影响；
- 窄屏：优先班级结论、待办和单学员详情，不压缩完整宽表。

### P4 训练方案列表与编辑

**页面任务**：当培训负责人准备下一批训练时，帮助其复用、编辑、验证和发布一份可执行方案版本。

- 列表模式：方案身份、当前发布版本、最近更新时间、引用班级、草稿状态；
- 编辑模式：左侧任务顺序，主区编辑当前任务，按需打开真实学员预览；
- 主操作：发布方案版本；
- 次级操作：保存草稿、复制方案、预览、查看历史；
- 发布前必须展示完整性错误和影响范围；
- 不允许任意工作流、拖拽画布、通用资源中心或多层发布计划；
- 未保存离开、自动保存失败和并发冲突必须可恢复。

### P5 达标复核队列与详情

**页面任务**：当培训负责人确认新人是否达到基础训练标准时，帮助其基于完整证据和风险快速作出可审计决定。

- 页面模式：Process–Approval；
- 排序：红线/证据缺失、低置信度、多次补练、等待时间；
- 主操作：记录达标决定；
- 证据顺序：当前建议结论 → 风险与缺口 → 关键证据 → 全部任务与历史；
- 批量确认仅适用于满足低风险规则的对象，执行前显示数量和抽检要求；
- 正式结果不得只用 Toast 保存；决定后留在队列并显示下一项。

### P6 我的训练

**页面任务**：当新人进入产品时，帮助其在三秒内知道当前任务、通过条件、截止时间和下一步，并继续完成训练。

- 核心对象：当前 TrainingTaskView；
- 主操作：开始/继续当前任务；
- 核心信息：任务目标、预计时间、通过条件、进度、最近反馈；
- 路径结构只作为位置提示，不复刻管理员配置树；
- 处理中时说明当前阶段、可离开、结果位置和预计恢复方式；
- 已完成时显示正式结果状态，不制造继续使用入口。

### P7 训练任务

**页面任务**：当新人执行具体训练时，帮助其完成输入或录音、可靠提交并得到可恢复结果。

- `learn`：聚焦材料正文和完成条件；
- `quiz`：逐题或小组答题、自动保存、错误定位和提交确认；
- `record`：准备说明、设备检测、录制、试听、重录、上传、后台处理和结果；
- 浏览器录音草稿在刷新或可恢复失败后保留；
- 提交使用幂等键，未知结果时先查询状态而不是直接重复创建；
- 键盘、焦点、屏幕阅读器、200% Zoom 和触控流程必须完整。

## What I already know

- 单个新人只在阶段性培训期间使用产品；组织侧因持续招聘而重复使用。
- 每年 3 月、7 月有大批校招新人，其余月份陆续有少量社招新人。
- 产品价值不是学员毕业后的日活或留存，而是培训组织的规模化交付能力。
- 当前项目包含过多与最小新人训练闭环无直接关系的模块、配置面和兼容路径。
- 新产品应优先服务培训负责人，学员端保证顺利完成当前训练任务。
- 正式达标结论必须由有权限的培训负责人作出；AI 只能提供可追溯初评、证据和建议。
- 推荐采用有边界的重建：新业务模型与数据结构独立，旧系统冻结并作为回退；基础设施只通过窄 Adapter 按需复用。

## Assumptions (temporary)

- 当前系统没有必须原样迁移到新运行模型的活跃生产训练记录；如存在，则采用并行切换而不是一次性替换。
- 第一版只需要学习、答题和录音表达三种稳定训练任务。
- PPT 讲解、Demo 讲解和异步客户场景都是不同材料与评分合同下的录音表达任务，不是独立模块。
- AI Coach、Realtime 对练、Persona、RAG、通用配置中心和通用 LMS 能力不进入 MVP。
- 继续使用团队熟悉的 FastAPI、PostgreSQL 和 Next.js；不为重建引入新技术栈。

## Open Questions

### 当前唯一架构阻塞问题

当前旧系统是否已经正式上线，并存在必须保留或继续运行的活跃班级、正式训练结果或审计数据？

- **若没有**：推荐新建独立仓库和独立业务 Schema，不迁移旧训练历史，仅按需导入已验证材料；
- **若有**：推荐新旧并行，旧系统只承接存量班级，新系统承接新班级，再对必要历史做显式迁移；
- 无论哪种情况，都不推荐长期双写或让新代码直接依赖旧业务 ORM。

### 试点前必须补齐、但不阻塞 PRD 方向的事实

- 第一版达标质量采用全量人工复核，还是“全量看摘要 + 风险对象深审 + 低风险抽检”；
- 校招峰值人数、小时级提交集中度、录音平均时长与培训团队人数；
- 当前人工培训人时、达标周期、返工、申诉和红线遗漏基线；
- 首次试点对应下一批真实新人，还是先用内部受控名单预演；
- 录音、转写、评测和审计数据的公司留存政策；
- 现有身份目录、对象存储、消息渠道和 AI Provider 中哪些已达到生产可复用标准。

## Detailed Functional Requirements

### R1. 训练方案草稿与发布

- 培训负责人可以创建、复制、重命名和归档 TrainingProgram。
- 一个 TrainingProgram 同时最多存在一个可编辑草稿；草稿保存使用显式版本校验。
- 草稿包含标题、适用对象、目标、预计总时长、有序 TrainingTask 和完成规则。
- 发布前执行确定性校验：任务顺序、材料可用、Quiz 答案、Record 评分维度、红线、允许次数、文件限制和评测能力。
- 发布成功生成完整不可变 ProgramVersion 快照；发布失败不移动当前发布指针。
- 新版本默认只供新 Cohort 或新 Enrollment 使用，不自动改变已开始训练。
- MVP 不提供跨资源原子 ReleasePlan；所有必要内容都编译进 ProgramVersion 或以不可变资产引用冻结。

### R2. 材料和任务内容

- 训练方案编辑时可从已有材料选择或在当前页面上传最小必要材料。
- 上传前校验文件类型、大小、组织范围和重复内容；失败保留任务草稿。
- 材料身份和版本对培训负责人可理解，学员只看到已冻结内容。
- Quiz 题目在方案内维护；MVP 不提供通用题库、AI 出题候选审核和跨方案题目运营。
- Record 评分表必须包含维度名称、用户语言说明、权重/通过规则、证据要求和红线。

### R3. 训练班创建与生命周期

- 创建 Cohort 时选择模式、名称、负责人、ProgramVersion 和日期策略。
- `scheduled` 必须有统一开始/截止时间；`rolling` 必须有个人训练周期长度。
- 草稿班可修改关键设置；启动后关键字段冻结。
- 暂停时学员只读已完成结果，不能开始新任务；恢复后从原状态继续。
- 关闭前展示未完成、处理中、补练、待复核和退出人数，要求逐类处理。
- 取消属于高风险动作，必须展示影响、填写原因并审计。

### R4. 学员导入、快速新建与分配

- 在 Cohort 详情中完成已有人员搜索、快速新建和 CSV 导入。
- 快速新建只要求姓名、唯一联系方式/员工标识和必要组织归属；其他资料可稍后补充。
- 导入流程为上传 → 字段预览 → 校验 → 影响预览 → 确认 → 逐项结果。
- 明确新增、已在本班、已在其他活跃班、字段错误、无权限和重复项。
- 批量写入具有 batch idempotency key；部分成功可只重试失败项。
- Enrollment 创建时冻结 ProgramVersion、日期和组织范围，并发送入训通知。

### R5. 学员 Journey 投影

- 后端返回单一 LearnerJourneyView，包含当前 TrainingTaskView、整体进度、截止时间、最近结果、后台任务和唯一 primary action。
- 学员不能自行跳过必修任务；任务按 ProgramVersion 顺序和完成条件解锁。
- `processing`、`needs_review` 和 `processing_failed` 具有明确用户语言和恢复动作。
- 没有 Enrollment、班级暂停、方案不可用、无权限和数据过期必须区分。
- 刷新、返回和多端打开不得创建重复 Submission。

### R6. Learn 执行

- 展示目标、内容、预计时间、完成条件和必要附件。
- 材料加载失败时保留当前位置并允许重试。
- 学员明确确认完成后生成 Submission；仅滚动或页面停留不能自动完成。
- 内容过长时提供目录和位置恢复，不把阅读拆成无业务意义的卡片。

### R7. Quiz 执行

- 支持单选、多选和判断，题目、答案、顺序、分值和通过线来自冻结版本。
- 答题自动保存本地与服务端草稿，网络失败不清空答案。
- 提交前说明未答数量；重复点击不创建重复 Submission。
- 判分由确定性规则完成，结果展示得分、错题对应知识点和下一步。
- 未通过时按方案允许次数重新提交；达到上限进入人工处理，不无限重试。

### R8. Record 录制、上传和评测

- 录制前显示任务目标、时限、评分维度和隐私说明，并完成麦克风权限/设备检查。
- 支持录制、暂停（如业务允许）、试听、重录和明确确认上传。
- 浏览器本地草稿在刷新、断网和可恢复上传失败后可找回；提交成功后按留存规则清理。
- 服务端校验类型、大小、时长、解码、静音和恶意内容；不信任前端元数据。
- 上传确认快速返回 AssessmentJob；转写和评分在后台执行。
- 后台任务可恢复、超时、重试、取消后续步骤并进入死信/人工处理，不因进程重启丢失。
- Evaluation 保存维度结果、引用证据、置信度、红线、模型/合同版本和安全错误。
- 学员看到结论、证据、建议和下一步；普通界面不显示模型名、Prompt 或原始 JSON。

### R9. 补练与重新提交

- 补练由确定性规则基于未通过任务和维度选择已发布材料或要求重录。
- MVP 不使用开放式 AI 自动生成任意训练路径。
- 每次补练明确原因、要完成的动作、允许次数和重新提交条件。
- 技术失败重试同一 AssessmentJob 或 Evaluation 流程；学习重试创建新的 Submission；两者不得混淆。
- 达到重试上限、重复红线或结果冲突时进入人工队列。

### R10. 待处理队列

- 队列聚合评测失败、低置信度、红线、多次未通过、逾期、待达标和批量导入失败。
- 每项包含类型、对象、班级、原因、影响、等待时间、当前状态和允许动作。
- 默认按风险优先级和等待时间排序；支持按班级、类型、状态和负责人筛选。
- 处理动作必须在对象上下文内完成；不得要求跳到技术日志、模型设置或其他模块后再返回。
- 系统故障和学员能力问题必须使用不同类别，防止把技术失败归因给学员。

### R11. 达标复核

- 复核视图只使用冻结 Submission、Evaluation 和历史 ReviewDecision。
- 正式决定必须校验培训负责人权限和 Enrollment 对象范围。
- 支持 `ready`、`remediation`、`evidence_required`、`deferred`；每种决定要求适当原因。
- 低风险对象可以批量确认，但批量动作必须预览数量、排除原因、抽检规则和结果。
- 任一低置信度、红线未处理、必修证据缺失或处理失败对象不得进入低风险批量确认。
- 新决定追加保存；更改决定必须引用被替代决定、原因和审计事件。

### R12. 通知与催办

- 触发入训、临近截止、逾期、评测完成、要求补练、需要补证据和正式达标通知。
- 通知规则使用确定性时间和状态，不由模型决定。
- MVP 至少支持站内通知；企业消息/邮件通过一个可替换 Adapter 接入，具体渠道待现状确认。
- 同一对象和事件去重，失败可重试，敏感信息不直接出现在外部通知正文。
- 培训负责人可在班级内对明确范围发送提醒，并查看发送结果和失败项。

### R13. 运营度量与结班报告

- 报告使用明确统计周期、数据新鲜度、分母和方案版本范围。
- 展示入训人数、按期达标率、达标周期、补练率、人工介入率、待处理积压和质量护栏。
- 培训人员工时基线通过明确采集方案建立，不使用不可解释的自动推算。
- 支持下钻到 Cohort 和 Enrollment，但遵守对象范围和敏感数据权限。
- 不展示与行动无关的排行榜、雷达图、装饰趋势或伪造“AI 洞察”。

### R14. 权限、审计与数据保护

- MVP 业务角色只有 Training Manager 和 Learner；平台管理员沿用外部身份平台，不扩展业务能力面。
- 后端校验组织、Cohort/Enrollment 对象范围和允许动作；隐藏按钮不构成权限。
- 录音、转写、评测和达标决定属于敏感员工训练数据，访问、下载、导出、重评和决定均审计。
- 文件使用短时访问地址；密钥、Provider 配置和内部错误不进入前端或普通日志。
- 审计记录 actor、action、target、before/after、reason、request/trace reference 和结果。
- 数据保留、删除、匿名化和导出策略必须在试点前经组织政策确认。

### R15. 新旧系统切换

- 新产品拥有独立业务 Schema、路由和 Interface，不从 Legacy 业务模块导入 ORM 或内部实现。
- 旧系统在试点期继续只读或按既有方式运行，入口通过 feature flag/路由配置切换。
- 只迁移仍在使用的材料、客观题、评分表、训练方案和必要活跃人员。
- 不迁移 Agent、Persona、RAG、Realtime、通用配置资产、Demo/Seed、旧 AI 会话和无法解释 lineage 的结果。
- 迁移执行 inspect → dry-run → conflict resolution → apply → verify；禁止长期双写。
- 试点失败可把入口切回旧系统，新系统数据保留用于诊断，不反向覆盖旧数据。

## AI Product Contract

### 为什么使用 AI

Record 任务涉及自然语言表达、事实覆盖、结构和沟通质量，不能完全依靠规则判定；AI 用于转写后的语义初评和可执行反馈。Quiz、截止时间、风险路由、状态流转和权限都使用确定性逻辑。

### 最小 AI 表面

- 后台自动评测（P0）；
- Record 结果页的结构化初评与证据（Object Result）；
- 培训负责人复核页的证据和低置信度提示；
- 不提供通用聊天、Agent Run、自然语言配置或生成式 UI。

### 输出 Schema

Evaluation 至少包含：

- `result`: passed / not_passed / needs_review；
- `dimension_results[]`: 维度、分值/等级、引用证据、改进建议；
- `fact_checks[]`: 事实、来源、匹配结果；
- `red_flags[]`: 类型、证据、严重级别；
- `confidence`: 总体及必要维度置信度；
- `limitations[]`: 缺失资料、音频质量或模型限制；
- `next_action`: pass / retry / human_review。

### 人工控制

- AI 不写 ReviewDecision；
- 低置信度和红线进入人工；
- 培训负责人可以接受、质疑或要求重评，但不能覆盖原始结果；
- Provider 失败不产生固定兜底分，不把失败展示为学员未通过；
- Prompt、模型、超时、重试、预算和数据允许范围由部署配置或窄治理模块管理，不成为培训负责人日常页面。

## Resilience and State Matrix

| 场景 | 用户可见行为 | 系统要求 |
|---|---|---|
| 导入部分成功 | 显示成功、重复、失败、跳过及逐项原因 | 只重试失败项，成功项不重复 |
| 上传超时但后端可能成功 | 显示“正在确认提交结果” | 通过幂等键查询，不直接重复创建 |
| 浏览器刷新/断网 | 恢复答案或录音草稿 | 本地草稿 + 服务端状态对账 |
| Provider 不可用 | 显示评测延迟或需要人工 | Job 重试、降级/人工路由，不伪造结果 |
| 低置信度转写 | 告知结果需要复核 | 不自动通过或正式评分 |
| 评测积压 | 班级显示延迟和受影响人数 | 队列容量、优先级、SLO 与通知 |
| 班级或方案并发修改 | 保留输入并显示差异/刷新要求 | expected version，禁止静默覆盖 |
| 权限被收回 | 清除敏感缓存并显示无权限 | 后端立即拒绝，前端不短暂泄露 |
| 数据过期 | 显示生成时间和刷新动作 | ViewModel freshness/version |
| 长任务取消 | 显示已保留的提交和停止范围 | 停止后续步骤，保留审计和可恢复状态 |

## Analytics and Product Events

只采集支持产品判断和运营恢复的事件：

- `program_draft_created`、`program_version_published`、`program_publish_failed`；
- `cohort_created`、`cohort_started`、`cohort_paused`、`cohort_closed`；
- `enrollment_import_previewed`、`enrollment_import_completed`；
- `training_task_opened`、`submission_saved`、`submission_finalized`；
- `assessment_queued`、`assessment_completed`、`assessment_failed`、`assessment_sent_to_review`；
- `remediation_assigned`、`resubmission_completed`；
- `review_decision_recorded`、`review_decision_superseded`；
- `notification_sent`、`notification_failed`；
- `exception_opened`、`exception_resolved`。

事件携带 organization、Cohort/Enrollment 的受控标识、ProgramVersion、时间和结果，不携带录音正文、完整转写、题目答案、密钥或敏感自由文本。

## Non-Functional Requirements

### 性能与容量

- 容量目标必须由 3 月、7 月真实峰值人数、提交集中度和培训团队容量确定。
- 普通列表、Journey 和班级状态查询在常见网络下快速返回并支持服务端分页。
- Record 上传确认与评测解耦；用户不等待完整转写和评分才能离开。
- AssessmentJob 提供队列时间、执行时间、重试和积压指标。
- 正式发布前执行基于真实峰值的导入、并发提交、上传、任务积压和复核队列测试。

### 可用性

- 核心训练写入可幂等重试；
- Worker 重启后 AssessmentJob 可恢复；
- 外部 Provider 故障时保留 Submission；
- 重要结果不依赖瞬时 Toast；
- 健康检查区分应用可用、评测能力可用和外部依赖降级。

### 可访问性和响应式

- 学员端支持常见手机、平板、桌面和 200% Zoom；
- 管理端核心运营和复核在窄屏可达，复杂批量编辑可明确建议桌面但不能丢失状态；
- 所有核心流程键盘可完成，焦点可见，表单有 Label，状态不只依赖颜色；
- Record 提供设备权限、录制状态和错误的可访问反馈；
- 支持 Reduced Motion，不使用持续 AI 动效。

### 安全和隐私

- 多租户组织隔离和对象级权限必须通过后端集成测试；
- 上传文件验证类型、大小、内容和恶意输入；
- 外部 AI 只接收完成评测所需的最小上下文；
- 敏感数据不写普通日志；
- 正式上线前确定录音、转写、评测和账号数据的保留/删除政策。

## Migration and Cutover Plan

### 数据分类

| 数据类别 | 默认策略 | 判断标准 |
|---|---|---|
| 活跃账号/组织身份 | 引用现有身份源，不复制密码和认证状态 | 身份源有稳定接口与对象范围 |
| 当前使用的培训材料 | 清理、去重、验证后导入 | 有明确所有者、用途、版本和权限 |
| 客观题与答案 | 转为方案内任务内容 | 仍用于 MVP，答案可验证 |
| Record 评分表/红线 | 人工审核后导入 | 业务语言清楚，能解释评测合同 |
| 活跃班级与在训记录 | 仅在确认必须连续运行时迁移 | 能建立完整映射并通过逐项对账 |
| 已结班正式结果/审计 | 默认旧系统只读保留；法规要求时专项迁移 | 不能丢失语义或审计链 |
| Demo、Seed、Mock 数据 | 不迁移 | 非正式业务事实 |
| Agent、Persona、RAG、Realtime、AI 会话 | 不迁移 | 不属于新产品边界 |
| 无 lineage 的分数/洞察 | 不迁移为正式结果 | 无法解释输入、版本和决定者 |

### 切换步骤

1. **盘点**：输出数据类别、数量、所有者、活跃引用、敏感等级和保留要求；
2. **映射**：每类数据明确新对象、字段映射、冲突规则和不可迁移原因；
3. **Dry-run**：只读导出并生成成功、冲突、跳过、失败报告，不写新系统；
4. **人工确认**：培训负责人确认材料、题目、评分表和活跃名单；
5. **试迁移**：在隔离环境执行，核对数量、抽样内容、权限与引用完整性；
6. **并行试点**：新班进入新系统，旧班继续旧系统；入口明确标识，禁止双写；
7. **正式切换**：达到试点门槛后把新班入口切到新系统；旧系统变为受控只读；
8. **退役评估**：满足保留周期和审计要求后，单独决策旧系统下线。

### 回滚原则

- 回滚只切换“后续新班从哪里创建”，不尝试把新系统产生的数据自动反写旧系统；
- 已在新系统启动的训练班优先在新系统完成，除非存在安全、数据一致性或核心不可用问题；
- 入口、通知和消息模板通过开关切换；数据库迁移不可作为唯一回滚手段；
- 回滚后保留新系统数据和审计用于诊断，暂停新写入，不宣称数据已消失。

## Pilot and Rollout Plan

### Gate 0：基线与合同确认

- 确认业务负责人、试点名单、方案内容、达标规则和人工复核口径；
- 完成人时、周期、质量和容量基线；
- 确认录音/转写留存、AI 数据范围和对象级权限；
- 明确旧系统是否有活跃生产数据。

### Gate 1：内部受控预演

- 用真实规模结构的内部账号走完定期班和滚动班；
- 演练批量导入部分失败、重复提交、断网上传、Provider 故障、低置信度、红线、补练和决定变更；
- 培训负责人完成一次方案发布、异常清零、正式复核和结班报告；
- 所有关键数据可审计且未发生跨组织访问。

### Gate 2：小范围真实试点

- 优先选择业务影响可控、培训负责人愿意记录实际人时的一批新人；
- 第一轮默认所有正式达标由人工确认，系统只减少资料整理与低价值批改；
- 每日检查评测积压、技术失败、人工队列、异常恢复和学员阻塞；
- 与同期/历史可比人工流程比较，不以主观“更智能”判断成功。

### Gate 3：校招峰值放量

- 在真实峰值压测、灾难恢复、权限、安全和成本门槛通过后进入；
- 先按班级或组织灰度，不按随机用户切割同一班级；
- 高峰期间冻结非必要方案结构变更，保留快速停用 AI 初评并转人工的能力；
- 每日关注积压 SLO、失败率、人工介入率、红线和申诉。

### 继续放量门槛

- 核心学习提交和正式决定无数据丢失、重复写入或越权；
- 技术失败没有被记为学员未通过；
- 培训人员工时或达标周期至少一项相较基线改善，另一项不显著恶化；
- 抽检、推翻、红线和申诉指标在业务确认的质量护栏内；
- 培训负责人能够在约定时限内清理异常队列，峰值积压可恢复。

### 暂停或回滚触发条件

- 跨组织/跨班级数据泄露或对象级权限失效；
- Submission、ReviewDecision 或审计记录丢失、错误覆盖或不可解释；
- AI/技术失败被系统性显示为学员能力未通过；
- 评测积压超过业务可接受窗口且无法降级到人工；
- 质量护栏明显恶化，继续放量会扩大错误决定；
- 培训负责人实际工时高于旧流程且原因不是短期上手或试点测量成本。

## Delivery Slices

实施按可演示、可验收的纵向切片推进，避免先建设通用平台再等待业务接入。

| 切片 | 可验证结果 | 主要范围 |
|---|---|---|
| S0 业务骨架 | 能创建组织范围内的方案草稿、发布版本和训练班 | 核心模型、权限、审计、路由骨架 |
| S1 Learn 闭环 | 一名学员从入训到完成材料任务，状态可恢复 | Enrollment、Journey、Learn、基础通知 |
| S2 Quiz 闭环 | 可靠保存、提交、判分、补练，无重复 Submission | Quiz、尝试次数、反馈、幂等 |
| S3 Record 闭环 | 录音上传后异步得到结构化初评，故障可恢复 | 上传、AssessmentJob、Evaluation、AI Adapter |
| S4 运营闭环 | 培训负责人可运营班级、处理异常并完成达标复核 | 待办、班级详情、ReviewDecision、批量安全 |
| S5 双节奏与结班 | 定期班和滚动班都可运行并生成业务指标 | 日期规则、提醒、报告、基线口径 |
| S6 试点与切换 | 内部预演和真实试点达到放量/回滚可决策状态 | 迁移工具、开关、压测、安全、运行手册 |

每个切片都必须包含前后端、权限、状态、审计、自动化测试和实际渲染检查；不能以“后端接口已写完”或“页面能打开”作为切片完成。

## MVP Acceptance Criteria

### 训练方案

- [ ] 培训负责人可以从空白或已有方案创建草稿，并配置至少一个 `learn`、`quiz`、`record` 任务。
- [ ] 材料、客观题答案、通过线、允许次数、Record 评分维度、事实来源和红线缺失时，发布被阻止且输入完整保留。
- [ ] 发布成功生成不可变 ProgramVersion；后续编辑不会改变已绑定班级和历史结果。
- [ ] 培训负责人可以在发布前预览学员视角、任务顺序、完成规则和版本影响。

### 双节奏开班与分配

- [ ] 定期班按统一起止时间运行；滚动班按每名学员加入时间计算个人截止时间。
- [ ] 培训负责人可以在班级内搜索已有人员、快速新建最小资料或 CSV 导入，无需跳到账号模块。
- [ ] 导入前能够预览新增、重复、冲突、无权限和错误项；确认后逐项展示结果并只重试失败项。
- [ ] 重复确认、页面刷新或网络重试不会重复创建 Enrollment 或发送重复入训通知。

### 学员执行

- [ ] 学员进入产品后三秒内能看到唯一当前任务、通过条件、截止时间、整体进度和主操作。
- [ ] Learn 只有在明确完成后产生提交；Quiz 答案在可恢复失败后仍存在，且由冻结答案确定性判分。
- [ ] Record 在录制前完成权限/设备检查，可试听、重录和确认上传；刷新或可恢复失败不会无提示丢失草稿。
- [ ] 上传未知结果时系统先查询幂等提交状态，不直接创建第二份 Submission。
- [ ] `processing`、`needs_review`、`processing_failed`、班级暂停、无权限和数据过期都有不同说明与恢复动作。

### 评测、补练与人工处理

- [ ] Record 提交后快速返回持久 AssessmentJob，Worker 重启或 Provider 暂时失败后任务仍可恢复。
- [ ] Evaluation 包含维度结果、证据、事实检查、置信度、红线、限制和下一步，且能追溯输入与评测合同版本。
- [ ] 技术失败不消耗学习尝试次数，也不被展示为学员未通过。
- [ ] 未通过反馈明确薄弱项、补练材料、允许次数和重新提交条件；达到上限进入人工队列。
- [ ] 红线、低置信度、多次未通过、技术失败、逾期和待达标对象按风险与等待时间进入不同类别。

### 正式达标与审计

- [ ] 只有有对象权限的培训负责人可以作出 `ready | remediation | evidence_required | deferred` 决定。
- [ ] AI 初评不能自动生成或覆盖 ReviewDecision；正式决定变更以追加记录替代原决定并要求原因。
- [ ] 批量达标执行前显示目标、排除项和抽检要求，且自动排除红线未处理、低置信度、证据缺失和技术失败对象。
- [ ] 关键查看、下载、重评、批量操作和正式决定均可追溯操作者、对象、原因、前后状态和结果。

### 运营结果与质量

- [ ] 训练班详情能回答是否按计划、谁在阻塞、当前最高风险、待处理数量和下一关键日期。
- [ ] 班级关闭前必须处理或明确标记未完成、处理中、补练、待复核和退出对象。
- [ ] 结班报告能按明确分母和方案版本计算单位培训人时、达标周期、按期达标、补练、人工介入和质量护栏。
- [ ] 首个真实试点有可比较的人工流程基线，不用 DAU、AI 调用次数或任务总数替代产品成效。

### 安全、韧性与切换

- [ ] 组织、班级和 Enrollment 对象级权限通过后端集成测试，前端隐藏不是唯一防线。
- [ ] 部分成功不显示为全部成功；重要结果不只通过 Toast 告知；敏感内容不进入普通日志或外部通知正文。
- [ ] 峰值容量测试使用真实业务基线规模，覆盖批量导入、集中提交、录音上传、评测积压和批量复核。
- [ ] 新旧系统在试点期保持单一班级权威；入口可回切旧系统且不破坏旧数据，不存在长期双写。
- [ ] 学员核心流程通过常见手机/桌面、键盘、可见焦点、屏幕阅读器基本检查和 200% Zoom 验证。

## Definition of Done (team quality bar)

- 自动化测试覆盖定期班、滚动入职、异步评测失败恢复和人工复核关键路径。
- 类型检查、lint、构建、单元测试、集成测试和关键 E2E 通过。
- 后端权限、对象范围、幂等、并发、审计和敏感数据处理通过验证。
- 实际渲染界面完成宽屏、窄屏、键盘、焦点、长文本、真实规模数据与错误状态检查。
- 发布、灰度、回滚、旧数据保留和失败降级方案已演练。
- 业务试点能够与旧人工流程比较培训人员工时、达标周期和质量结果。

## Out of Scope (explicit)

- 通用 LMS、知识库、RAG、Agent、Persona、Situation Pack 和模型配置平台。
- 实时语音角色扮演、聊天式 AI Coach 和毕业后的持续销售能力平台。
- 通用低代码流程、通用资源联合、跨领域 ReleasePlan 和任意页面搭建器。
- 为兼容旧接口而复制 Legacy 数据模型或长期双写、双读。
- 以 DAU、毕业后留存、训练次数或 AI 使用次数作为产品成功标准。
