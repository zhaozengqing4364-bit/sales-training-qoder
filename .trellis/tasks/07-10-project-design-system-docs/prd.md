# 项目设计语言、Token 与品牌规范文档

## Goal

基于仓库现有前端实现、设计资产与业务定位，整理当前项目的设计语言、Design Token 和品牌规范，并补足缺失的决策，形成可供产品、设计与研发共同使用的 Markdown 单一事实源。

## What I already know

- 用户要求整理当前项目已有的设计语言、Token 与品牌规范，并生成对应的 Markdown 文档。
- 文档必须以仓库真实实现为基线，区分“已存在”“建议统一”“待迁移”，不能把新设计伪装成现状。
- 普通用户界面不得泄露工程术语、测试字段或内部错误码。
- 业务页面应遵守上下文内完成原则，并覆盖完整交互状态与基础可访问性。
- 仓库已经存在 `web/design-system/sales-trainer/DESIGN.md`、分层 CSS Token、`tokens.json` 与 showcase，但这些 Token 未被生产样式导入或消费。
- 生产界面已有稳定的 Modern Soft UI 基线：Slate/Stone 中性色、半透明白色表面、超大圆角、低对比阴影、深色锚点按钮和粉彩状态色。
- 当前品牌名称至少存在“AI 智能练习平台”“AI 销售教练”“新人训练路径”“企业新人训练路径平台”四种口径。
- `CONTEXT.md` 已确认 `sales_trainer` 只是兼容技术命名，用户可见产品名必须使用“新人训练路径”。

## Assumptions (temporary)

- 目标产物应同时服务设计决策与工程落地，而非仅做品牌宣言。
- 默认优先复用现有品牌资产和组件体系，不直接修改生产 UI。
- 本轮只生成规范文档与必要审计记录，不实施大规模样式迁移。

## Open Questions

- 品牌架构应以“企业新人训练路径平台”为统一主品牌，还是保留“AI 智能练习平台 / AI 销售教练”作为母品牌、将“新人训练路径”作为产品线？

## Requirements (evolving)

- 审计颜色、字体、字号、间距、圆角、阴影、层级、布局、动效、图标、组件和交互状态。
- 审计 Logo、品牌名称、品牌主张、语气与用户语言。
- 给出语义 Token、组件 Token、命名规则和迁移原则。
- 明确 Do / Don't、可访问性、响应式与品牌治理方式。
- 所有结论提供代码或资产路径依据。

## Acceptance Criteria (evolving)

- [ ] 文档包含设计语言、品牌核心、Token、组件规则、状态、响应式、动效与治理章节。
- [ ] 每个核心 Token 均有明确名称、值、语义与使用场景。
- [ ] 明确区分现状、目标规范与迁移项。
- [ ] 文档中的关键值能追溯到现有代码，或明确标记为新设计决策。
- [ ] 不覆盖或混入用户当前工作区的无关改动。

## Definition of Done (team quality bar)

- Markdown 结构完整、无占位符、无自相矛盾。
- 关键 Token 与品牌资产完成源码交叉验证。
- 文档路径稳定、可被后续开发任务引用。
- 给出发布使用方式、风险等级与回滚方式。

## Out of Scope (explicit)

- 未经确认不修改现有页面、组件或样式配置。
- 不在本任务中完成全站 Token 迁移或视觉重构。
- 不新增字体、图标或 UI 依赖。
