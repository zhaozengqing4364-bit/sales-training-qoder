# brainstorm: 多账号体系与销售组长工作台

## Goal

建设可正式交付的多账号开通与销售组长只读工作台：管理员能够安全、可审计地批量创建销售成员及组长、维护团队归属；销售组长登录后只能查看其授权团队的成员任务、训练进度和团队洞察，并可下钻理解风险，但本期不能发布或变更训练任务。

## What I already know

* 用户希望近期为多人创建账号，并关注账号体系与销售组长视角是否已可用。
* 后续会提供 HTTPS 域名；本任务先处理不依赖域名的账号、组织、权限和工作台问题。
* 当前前端创建用户提交 `display_name`，后端 `CreateUserRequest` 要求 `username`，真实契约不一致。
* 后端校验了初始密码，但创建用户时没有持久化 `hashed_password`。
* 用户管理接口仅允许 `user`、`support`、`admin`，无法创建已有角色词汇中的 `training_manager` 或 `training_lead`。
* 当前没有 CSV 批量开户、导入预览、逐行校验、邀请激活、重发邀请和批次审计闭环。
* 密码重置默认使用控制台邮件实现，尚不具备正式通知能力。
* 销售组长页面 `/team` 已有团队进度列表和学员详情，但主要是只读视图。
* 组长角色在前端路由、销售训练权限、训练任务服务和主管服务中的定义不一致，没有任何单一角色能走通“开户—登录—看团队—分配任务—审核/重训”全链路。
* 当前团队数据范围依赖自由文本 `department` 精确相等；没有 Team、TeamMembership 或直属组长关系。
* 较丰富的审核、校准、重训和团队洞察能力已经存在于管理员主管模块，但尚未按团队范围开放给销售组长。

## Confirmed Scope and Defaults

* 账号主要面向公司内部销售人员和销售组长，不面向外部客户自助注册。
* MVP 需要支持一次创建多名成员，而不是仅修复单账号表单。
* 销售组长只能管理明确授权给自己的团队，不能仅靠同名部门自动获得全量访问权。
* 临时密码默认有效期为 72 小时并支持配置；过期后管理员只能重置，不得恢复或查看旧密码。
* 团队洞察基础指标按团队规模/训练覆盖、任务进度、逾期停滞、完成与通过质量、薄弱维度和受影响成员设计。
* 销售组长本期为只读角色，不创建、分配、修改、取消或重发训练任务。

## Requirements

* 统一用户创建、更新和角色分配的前后端契约与角色词汇。
* 支持多人导入前预览、去重、字段校验、权限校验、确认创建、逐行结果和可审计批次。
* 账号创建和临时密码重置必须幂等，失败可重试，不得明文保存或记录密码、令牌。
* 组长权限必须由后端做对象级校验，不能依赖前端隐藏入口。
* 组长应在当前团队工作台内完成团队概览、成员任务与进度查看、洞察筛选和成员下钻，不被迫跳往平台管理员模块。
* 普通界面不得展示 UUID、内部枚举、测试数据或原始错误。
* 本期销售组长工作台必须包含团队成员与训练覆盖、已分配任务、个人/团队进度和团队洞察，全部为只读能力。
* 团队洞察必须能够下钻到授权团队内的相关成员，并从洞察直接进入成员详情或该成员的任务列表。
* 组长角色不得调用训练任务创建、批量分配、更新、取消、重发或团队结构治理接口；后端必须返回 403，不能只隐藏前端按钮。
* 本期保留并修复平台管理员基于已发布训练模板的单人/批量任务分配；销售组长只查看分配结果。
* 管理员分配成功后，任务必须立即进入对应组长的授权团队任务视图和洞察统计；跨团队组长不可见。
* 任务分配 application service 必须与调用角色解耦：本期 policy 仅允许平台管理员，下一版可在不改变任务契约的前提下增加受 Team Scope 限制的组长权限。
* 本期正式认证方式为账号密码登录；账号创建后无需等待企业微信或外部身份源同步即可登录。
* 本期唯一登录账号为公司邮箱；前端统一标注为“账号（公司邮箱）”，不新增独立用户名登录。
* 邮箱在导入、单个创建、登录、密码重置和未来外部身份绑定前统一执行 trim + lowercase；数据库按规范化值保证唯一。
* 批量开户最小必填字段为姓名、公司邮箱、系统角色和团队标识；员工编号、部门展示名等辅助字段可选。
* 导入预览按规范化 `team_code` 分组；已存在团队显示匹配结果，不存在团队允许在当前预览页补充团队名称并就地创建。
* 每个新团队必须在确认前从现有账号或本批次组长账号中指定一名主组长；候选账号必须具备销售组长角色且处于可激活状态。
* 未匹配团队、重复团队代码、无主组长、组长账号冲突或成员跨团队冲突必须在预览中逐项显示；不得静默创建或自动猜测归属。
* 预览修改、返回和再次进入应保留已完成的团队映射与主组长选择，直到批次确认、取消或过期。
* 批次确认以团队为事务原子：同一团队本次新增的账号、Team、主组长关系和成员关系全部成功后才提交，否则该团队本次写入全部回滚。
* 不同团队允许部分成功；批次状态至少区分 validated、processing、completed、partially_completed、failed、cancelled/expired。
* 每个批次和团队执行单元拥有稳定幂等键；使用原批次重试只处理失败团队，不重复创建已成功账号、关系或审计事件。
* 结果页逐团队、逐账号展示 created/skipped/failed 及用户可理解原因；只对成功创建且需要首次登录的账号返回一次临时密码。
* 销售组长的规范后端角色采用现有 `training_manager`，界面统一显示“销售组长”；`support`、`training_lead` 不再作为团队数据访问的隐式别名。
* 密码必须使用项目统一的安全哈希策略持久化，任何 API、审计和应用日志不得记录明文密码。
* 批量开户由系统为每个用户生成不同的加密安全随机临时密码，禁止管理员设置统一默认密码。
* 临时密码仅在开户结果中显示一次；如需下载，文件由当前响应在客户端生成，不在服务端保存明文凭据文件。
* 用户使用临时密码首次认证后必须先设置新密码，完成前不得进入训练或管理业务页面。
* 首次展示结束后管理员不得查询原临时密码，只能发起生成新临时密码的重置操作；旧临时密码立即失效。
* 临时密码展示、下载和重置必须二次确认、检查管理员权限并写入不含密码内容的审计记录。
* 确认响应丢失、页面刷新或管理员未保存凭据时，系统只显示账号已创建和“凭据不可再次查看”，提供批量重置临时密码的恢复动作，不尝试找回旧密码。
* 新增独立 Team、TeamMembership 和 TeamLeaderAssignment；`User.department` 不再作为团队对象权限依据。
* 全部组长读取通过集中 Team Scope Policy 校验 TeamMembership/TeamLeaderAssignment；后续新增组长写入能力也必须复用同一策略，禁止各服务自行比较部门字符串。
* Team、成员关系和组长关系记录生效/失效时间、操作者及变更原因；调组与撤权保留历史，不物理删除业务关系。
* 现有部门数据迁移前必须提供 dry-run 映射报告，未匹配、重名、空部门和冲突数据不得静默处理。
* 每名学员同一时间只能有一个有效主团队；更换主团队必须原子化结束旧关系并建立新关系。
* 每个有效团队必须有一名主组长，可配置多个协同或代理组长；同一组长可同时负责多个团队。
* 主组长与代理组长的权限差异必须集中配置；MVP 默认均只能查看成员、任务、进度和洞察，任务发布及团队治理动作仅平台管理员可执行。
* 团队洞察支持最近 7 天、30 天、90 天和自定义时间范围，默认最近 30 天。
* 洞察同时计算上一同长度周期作为对比基线；当前周期与对比周期必须使用相同 Team Scope、训练范围、时区和状态口径。
* 周期对比至少覆盖训练覆盖/完成率、逾期或停滞人数、平均成绩/通过质量和主要薄弱项；无基线时显示“暂无可比数据”，不得伪造 0% 变化。
* 组长负责多个团队时，首页默认汇总全部有效授权团队，并提供单团队筛选；只有一个团队时不显示无意义选择器。
* 团队筛选必须同步作用于概览、周期对比、任务状态、薄弱项、成员列表和下钻链接；缓存键及导出/分享状态（如后续增加）也必须包含同一范围。
* 多团队汇总按 learner_id 去重；历史成员或重叠异常关系不得导致人数、完成率或薄弱项重复计数。
* 新人训练路径与管理员额外分配任务是两个独立业务对象，分别展示完成率、状态分布、逾期/停滞和下钻列表，不计算综合百分比。
* 成员详情以统一时间线呈现路径活动、额外任务和训练结果，但每条记录保留来源类型、原始状态口径和对应详情入口。
* 团队洞察的路径指标只使用当前发布路径及有效 enrollment；额外任务指标只使用管理员分配的有效 TrainingTask，取消/过期状态按各自规则单独解释。
* 团队洞察不提供个人分数排行榜；以“逾期或停滞”“完成质量未达发布标准”“主要薄弱项”等可解释分组展示需要关注的成员。
* 风险分组使用确定性业务规则：逾期来自任务截止时间，停滞来自选定周期内未推进且仍有未完成必修项，质量未达标来自发布版本通过标准；不得由 AI 猜测风险。
* 每个风险分组显示定义、涉及人数、变化趋势和成员下钻；完整成员列表独立提供姓名/邮箱搜索和状态筛选，不按分数制造排名。

## Acceptance Criteria

* [ ] 管理员可预览并确认一次创建至少 50 个账号，重复提交不产生重复用户。
* [ ] 邮箱、企业微信 ID、员工标识冲突会在确认前逐行显示，并提供可执行修正说明。
* [ ] `User@Example.com`、`user@example.com` 和带首尾空格的同一邮箱只能对应一个账号，导入、登录与重置密码使用一致结果。
* [ ] 登录页、批量模板和开户结果明确说明账号是公司邮箱，不出现含义冲突的 username/display_name 字段。
* [ ] 导入文件中的未知 `team_code` 可在预览页内完成团队名称和主组长配置，无需离开开户流程。
* [ ] 未指定有效主组长的团队无法确认；错误精确定位到团队和关联行，修正后可原地重新校验。
* [ ] 新团队、账号、成员关系和主组长关系在确认后正确关联，审计记录能够还原批次和操作者但不包含临时密码。
* [ ] 同一团队任一运行时写入失败会回滚该团队本次全部新增数据，其他团队仍可成功，批次状态为部分完成。
* [ ] 对失败团队使用同一批次重试只补齐失败单元；并发点击确认或重试不会产生重复账号、团队关系或审计事件。
* [ ] 回滚团队不会返回或保留无效临时密码；已成功团队的凭据不会在重试响应中再次泄露。
* [ ] 创建的成员和销售组长能够通过选定的正式登录方式完成首次登录。
* [ ] 批量创建成功的用户可以使用分配的账号与初始密码登录，首次登录状态及后续密码生命周期符合最终确认规则。
* [ ] 每个新用户获得不同临时密码；数据库仅保存哈希，响应之外的日志、审计、任务记录和导出存储均无明文。
* [ ] 临时密码只能完成一次首次认证；用户改密后旧密码失效，未改密用户不能访问业务 API。
* [ ] 管理员离开结果页后无法再次查看原密码，执行重置会生成新密码并使旧密码失效。
* [ ] 模拟提交成功但响应中断、结果页刷新和未导出离开后，账号状态保持正确，管理员可批量重置且旧临时密码失效。
* [ ] 销售组长角色从创建、登录跳转、导航、接口权限到业务动作保持一致。
* [ ] 组长只能查看授权团队成员，跨团队直接访问返回无权限或不可见。
* [ ] 修改用户 `department` 不会自动扩大组长权限；只有有效团队关系能授予对象范围。
* [ ] 团队成员调组、组长授权和撤权立即影响列表、详情、任务可见范围和洞察查询，并保留历史审计。
* [ ] 数据库约束和并发测试保证同一学员不会同时出现两个有效主团队、同一团队不会同时出现两个有效主组长。
* [ ] 主组长、代理组长和跨多个团队的组长分别通过权限回归测试，数据不会串组。
* [ ] 旧数据回填支持 dry-run、重复执行和冲突报告，回滚不会删除用户或训练记录。
* [ ] 停用、调组、撤销组长权限后，访问范围立即生效且保留审计记录。
* [ ] 批量开户、角色变更和团队变更都有可理解的审计记录。
* [ ] 组长可查看团队训练覆盖率、总体进度、逾期/停滞成员和主要薄弱项，并下钻到对应成员。
* [ ] 组长可切换 7/30/90 天或自定义区间，所有洞察卡片与下钻列表同步使用同一筛选条件。
* [ ] 当前周期与上一同长度周期的边界、Asia/Shanghai 时区、空基线和跨日数据有自动化口径测试。
* [ ] 多团队组长默认看到全部授权团队的去重汇总，切换单团队后所有卡片、列表和下钻数据同步变化。
* [ ] 撤销某团队授权后，该团队立即从默认汇总和筛选项消失，旧缓存不能继续返回其数据。
* [ ] 页面明确区分“新人训练路径”和“额外训练任务”，两者各自拥有可解释分母，任何位置都不展示混合综合完成率。
* [ ] 成员详情时间线可同时查看两类记录，但筛选、状态标签和详情链接不会混淆来源。
* [ ] 洞察页没有个人分数排行榜；风险成员只按可解释业务分组展示，每个成员都能看到进入分组的确定性原因。
* [ ] 风险规则边界、发布通过标准变化、同一成员命中多个分组和无风险成员场景均有自动化测试。
* [ ] 组长可查看授权成员的任务名称、来源、状态、截止时间和完成结果，但页面无任务发布/变更操作，直接调用写接口稳定返回 403。
* [ ] 平台管理员可从已发布模板为单人或多人分配任务，重复分配被跳过，部分失败逐项返回且审计不记录内部错误原文。
* [ ] 管理员新分配任务后，对应授权组长刷新即可看到结果；无团队关系或其他团队组长不能看到该任务。
* [ ] 达标审核和重训入口本期不展示不可用占位，不阻断进度、任务和洞察主流程。

## Definition of Done (team quality bar)

* Tests added/updated (unit/integration where appropriate)
* Lint / typecheck / CI green
* Docs/notes updated if behavior changes
* Rollout/rollback considered if risky
* 前后端真实契约测试覆盖开户和组长关键路径
* 权限矩阵、幂等、并发、部分失败和审计验证通过
* 新增核心团队模型和权限决策写入 ADR
* 按根目录 `DESING.md` 完成产品/交互验收，并复用 `web/design-system/sales-trainer/DESIGN.md` 的现有视觉 tokens 与组件

## Out of Scope (explicit)

* HTTPS 域名和证书部署，等待用户后续提供域名后单独处理。
* 面向外部客户的开放注册和社交账号登录。
* 在需求确认前，不修改正式用户数据或批量创建真实账号。
* 达标审核、评分校准和重训闭环，本期不接入销售组长工作台，作为下一期范围。
* 多层/嵌套团队、跨企业多租户和完整 SCIM 自动同步，本期不建设。
* 企业微信登录、IAM 对接、SAML/OIDC SSO 和 SCIM 自动账号同步，本期不建设，后续独立接入。
* 销售组长创建、批量分配、修改、取消或重发训练任务，本期不建设。
* 销售组长任务分配预计下一版接入；本期只预留统一 policy 和接口复用点，不提前展示入口。
* 独立用户名、手机号和员工编号登录本期不建设；员工编号只可作为可选业务标识。

## Decision (ADR-lite)

### 本期销售组长 MVP 边界

**Context**：账号体系和销售组长能力存在角色漂移、部门字符串授权和管理动作断链，需要先形成可独立验收的业务闭环，同时避免一次性接入所有主管能力。

**Decision**：本期完成批量开户、团队关系，以及销售组长只读的成员任务、训练进度和团队洞察；销售组长任务发布/变更、达标审核、评分校准与重训均不在本期。

**Consequences**：本期必须建立可扩展的团队对象级只读权限和洞察下钻契约，不在 UI 中放置任务发布、审核或重训占位；后续写能力复用相同 Team Scope Policy，不重新设计对象范围。

### 本期认证通道

**Context**：近期需要直接为多人开通可登录账号，企业微信、IAM 和 SSO 尚未进入本期实施范围。

**Decision**：本期采用应用内账号密码认证，批量开户完成后用户可直接登录。

**Consequences**：必须补齐初始密码交付、首次登录改密、密码重置、登录限流和账号停用策略；身份模型仍保留未来绑定外部身份主体的扩展位置，但本期不实现对应连接器。

### 初始密码交付

**Context**：本期没有企业微信、IAM、SSO 或正式邀请通知通道，但批量创建的账号需要安全完成首次登录。

**Decision**：系统为每人生成唯一一次性临时密码，仅在开户结果页显示或导出一次；用户首次登录必须改密，之后管理员不能查看，只能重置。

**Consequences**：需要显式的首次改密状态、临时密码过期/撤销语义、一次性明文响应和客户端导出；生产启用必须以 HTTPS 为发布门禁，服务端不得存储可下载的明文凭据文件。

### 团队授权模型

**Context**：现有实现以自由文本部门精确匹配组长与学员，无法可靠支持销售小组、调组、代理组长、撤权和对象级审计。

**Decision**：本期建立独立 Team、TeamMembership 和 TeamLeaderAssignment；全局角色决定可执行能力，显式团队关系决定可操作对象范围，部门降级为展示和导入辅助属性。

**Consequences**：需要新增 schema/migration、旧数据 dry-run 回填和集中 Team Scope Policy；现有 journey、training task、team insights 与前端 `/team` 必须统一迁移到该权限入口。

### 团队关系基数

**Context**：团队模型需要兼顾清晰归属、代理管理和一个组长负责多个小组，同时避免洞察统计因重复成员关系被重复计算。

**Decision**：学员同一时间仅有一个有效主团队；团队必须有且仅有一名有效主组长，可有多个协同/代理组长；组长可负责多个团队；全部关系采用有效期并保留历史。

**Consequences**：调组和更换主组长需要事务与并发约束；跨团队汇总必须按 learner 去重；代理组长不自动获得团队结构治理权限。

### 团队洞察时间口径

**Context**：只有当前快照无法判断团队训练状况是在改善还是恶化，且现有洞察查询虽支持日期参数，但缺少统一周期对比契约。

**Decision**：本期支持最近 7/30/90 天与自定义区间，默认 30 天，并计算上一同长度周期作为对比基线。

**Consequences**：需要统一 Asia/Shanghai 周期边界、当前/对比查询口径和无基线展示；日期过滤必须下推数据库，洞察缓存键必须包含团队、训练范围和时间区间。

### 训练任务分配权限

**Context**：本期需要让组长查看管理员分配后的真实任务结果，但销售组长暂不承担发布或变更任务职责；下一版预计很快开放组长分配。

**Decision**：本期仅平台管理员可以从已发布模板分配训练任务；销售组长只读授权团队的任务结果，所有任务写接口对组长返回 403。

**Consequences**：任务 application service 与授权 policy 必须分离，不能继续把角色集合硬编码在服务内部；下一版只扩展 policy 和组长 UI，不重写任务创建、幂等、逐项结果与审计契约。

### 登录账号标识

**Context**：当前认证接口原生使用邮箱，改为独立用户名会扩大到身份模型、唯一约束、密码重置和未来 SSO 绑定；用户确认本期可采用公司邮箱登录。

**Decision**：公司邮箱是本期唯一登录账号，所有入口统一 trim + lowercase，并以规范化值做数据库唯一约束和查询。

**Consequences**：需要清查现有大小写重复数据并在 migration 前输出冲突报告；修复前后端 `username/display_name` 契约时不再引入第二套登录标识；未来 IAM/SSO 可先以邮箱匹配后绑定稳定 external subject。

### 导入流程内建组

**Context**：批量账号通常与团队关系同时建立；若未知团队迫使管理员离开开户流程单独建组，会造成上下文丢失、重复导入和孤立账号。

**Decision**：导入预览按 `team_code` 分组；未知团队可在预览页就地补充并创建，且必须从现有或本批次账号中指定有效主组长后才能确认。

**Consequences**：预览模型需要稳定行 ID、团队草稿和跨行引用；确认编排必须按依赖顺序创建组长账号、Team、LeaderAssignment、成员账号和 Membership，并在审计中关联同一 provisioning batch。

### 批量开户事务边界

**Context**：整批原子会让一个团队的偶发错误阻塞所有团队，逐行提交又可能产生缺组长、缺成员关系的半成品团队。

**Decision**：以团队为原子执行单元，同一团队全成全败，不同团队允许部分成功；原批次仅重试失败团队并保持幂等。

**Consequences**：需要批次/团队/行三级状态、团队级事务编排和稳定幂等键；一次性凭据只属于最终成功行，失败回滚及重试不得重复返回已交付凭据。

### 销售组长规范角色

**Context**：当前 `support`、`training_lead`、`training_manager` 在不同模块被交叉视为组长，导致开户、导航和业务权限无法一致。

**Decision**：后端规范角色使用现有 `training_manager`，用户界面统一显示“销售组长”；其他角色不再通过兼容别名自动获得团队访问权。

**Consequences**：需要迁移/清查现有角色数据并统一前端路由、导航、Team Scope Policy 和接口权限测试；平台支持人员如需查看团队，必须显式获得平台管理员能力或团队组长关系，不依赖角色别名。

### 多团队默认视图

**Context**：同一组长可以负责多个团队，强制逐团队查看会降低总览效率，但不受控汇总容易重复计数或造成筛选口径不一致。

**Decision**：首页默认汇总全部有效授权团队并允许切换单团队；只有一个团队时隐藏选择器，多团队汇总按 learner_id 去重。

**Consequences**：所有洞察查询、周期对比、下钻和缓存必须携带相同 team scope；授权撤销需要使相关缓存立即失效，不能仅等待默认 TTL。

### 训练进度口径

**Context**：新人训练路径按阶段/模块/活动计算进度，管理员额外任务按任务状态与截止时间计算进度，二者分母和状态机不同。

**Decision**：组长视图分开呈现“新人训练路径”和“额外训练任务”，不合成综合百分比；成员详情仅在时间线上统一编排展示，仍保留来源和原始语义。

**Consequences**：洞察 API/ViewModel 需要两个明确聚合对象，前端不得为了单一大数字混合计算；未来新增任务类型时按来源扩展，不改变历史指标含义。

### 团队洞察呈现原则

**Context**：个人分数排行榜会把不同任务、阶段和样本量强行比较，难以支持组长判断下一步关注对象，也容易诱导错误竞争。

**Decision**：不展示个人分数排行榜；使用确定性规则形成可解释风险分组，展示原因、人数、趋势和成员下钻，同时保留不按分数排序的完整成员列表。

**Consequences**：风险规则必须引用任务截止时间、路径状态和发布通过标准，不使用 AI 推断；同一成员可命中多个分组，聚合人数与全团队人数必须分别解释。

### 设计真源

**Context**：仓库根目录存在规范性文件 `DESING.md`，用户明确确认本任务以该文件定稿；销售训练目录另有既有视觉 token 规范。

**Decision**：根目录 `DESING.md` 是本任务产品设计与工程行为真源；`web/design-system/sales-trainer/DESIGN.md` 及其 tokens 是项目现有视觉基础，按前者的权威关系复用。

**Consequences**：页面模型、信息密度、导入/批处理、Dashboard–Drilldown、状态韧性、URL、可访问性和 QA 按 `DESING.md` 验收；视觉上复用既有画布、状态色、圆角、阴影、间距、焦点和组件，不发明局部设计系统。

## Technical Approach

### Identity and password lifecycle

* 保留 `User.is_active` 作为账号启停状态，新增集中管理的密码状态（temporary/active/reset_required）、临时密码过期时间和最近改密时间。
* `hashed_password` 是本期密码权威来源；环境共享密码和逐邮箱环境密码只保留兼容读取，禁止新账号依赖兼容模式，并制定后续清理计划。
* 临时密码认证成功后只签发短期、限权的改密凭证；仅允许访问改密、退出和必要身份接口。改密成功后才签发正式会话。
* 登录、创建、导入和重置统一调用邮箱规范化与密码 policy；登录限流、失败计数和临时密码有效期均配置化并记录脱敏安全事件。
* 批量开户仅允许创建“学员”和“销售组长”业务角色；平台管理员及其他高权限角色继续走独立、受控的管理员流程。

### Team domain and authorization

* 新增 `Team`（稳定 code/name/status）、`TeamMembership`（learner/team/effective range）和 `TeamLeaderAssignment`（primary/assistant/effective range）。
* 数据库约束保证每名学员最多一个有效主团队、每个有效团队恰有一名主组长；application service 使用事务完成调组和主组长替换。
* 新增集中 `TeamScopePolicy`：规范角色决定是否具备组长读取能力，LeaderAssignment 决定可访问 Team，Membership 决定可访问 Learner/Task/Insight。
* journey、training task、team insights 和 `/team` 统一消费 TeamScopePolicy；不再保留部门字符串的隐式授权分支。

### Provisioning batch

* 管理后台提供 UTF-8 CSV 模板、上传解析、无写入校验预览、团队映射/就地建组、确认执行、进度与结果页面。
* 新增 `ProvisioningBatch`、团队执行单元和行结果模型，保存源文件哈希、稳定行 ID、幂等键、状态、用户可理解错误码和关联对象 ID；不保存明文密码。
* 确认时按团队事务编排：先处理主组长账号，再创建/匹配 Team 与 LeaderAssignment，最后创建成员账号与 Membership；不同团队独立提交。
* 一次性凭据只存在于成功确认/重置响应的内存结果中，由浏览器客户端生成 CSV；响应丢失后通过批量重置恢复。
* API DTO 统一使用 `name/email/role/team_code` 等业务字段，经过 Domain Model 与 ViewModel 后进入 UI，移除当前 `username/display_name` 歧义。

### Administrator task assignment

* 复用现有已发布模板与课程计划校验，修复权限、批量查询、重复判断、幂等和逐项结果。
* 本期 task write policy 仅允许平台管理员；销售组长只能通过 Team Scope 读取授权成员的任务结果。
* 任务 application service 不硬编码角色字符串，为下一版组长分配预留独立 policy 扩展点。

### Team read model and insights

* 新建按 Team Scope 查询的只读 application/query service，所有团队和日期条件下推数据库，禁止先加载全量数据再内存过滤。
* 返回两个独立聚合：`newcomer_path_progress` 与 `assigned_training_tasks`；成员时间线只做编排，不混合状态机和分母。
* 洞察支持全部授权团队/单团队、7/30/90 天/自定义区间及上一同长度周期，统一 Asia/Shanghai 边界。
* 风险分组完全由任务截止时间、路径推进状态和发布通过标准计算；返回规则说明、当前值、对比值、成员 ID 集合与下钻条件。
* 明确不查询或返回 readiness、calibration、retraining 写能力；这些字段不进入本期 DTO，避免仅靠前端隐藏。

### Page models and states

* 批量开户页主流程为：下载模板 → 上传/校验 → 团队分组与就地补全 → 确认 → 执行进度 → 部分成功结果 → 一次性凭据保存/恢复。
* 销售组长页主任务为“判断哪些团队或成员需要关注以及原因”：顶部放团队/周期筛选；主体分开呈现路径进度、额外任务、风险分组和完整成员列表。
* 组长页没有发布任务主按钮、禁用占位或管理入口；管理员分配任务后，组长只读结果自然进入任务区和洞察。
* 两个页面覆盖 loading、empty、no-result、permission denied、partial success、failure/retry、stale/conflict、interrupted/credential-lost 等相关状态，重要结果不能只用 toast 表达。
* UI 以根目录 `DESING.md` 为行为规范，复用 `web/design-system/sales-trainer/DESIGN.md` 的 tokens 与现有组件，保持企业信息密度，避免卡片墙和游戏化排名。

### Migration, rollout, and rollback

* 先执行只读 dry-run：报告邮箱大小写冲突、角色别名、部门到团队候选映射、缺失主组长和重叠关系；未解决冲突不切换权限权威。
* migration 仅新增字段/表/索引并可重复执行；旧字段和数据先保留，Team Scope 完整性检查通过后再开启新读取路径。
* 使用可快速关闭的 feature flags 分别控制批量开户、新 Team Scope 和团队洞察；生产开放账号密码及一次性凭据前必须完成 HTTPS 门禁。
* 回滚以关闭 feature flag、恢复旧读取入口为主，不删除新表、账号、团队或训练记录；任何已创建账号需要显式停用而非回滚脚本物理删除。
* 记录 requestId/traceId、批次/团队/行耗时、成功/跳过/失败计数、安全事件和不含敏感数据的审计记录。

## Page Specifications

### 管理端批量开户

* **页面任务**：当平台管理员集中开通销售团队时，帮助其校验账号与团队关系、安全完成开户，并获得可追踪的逐项结果。
* **核心对象**：ProvisioningBatch、团队执行单元、导入行、User、Team、Membership、LeaderAssignment、一次性凭据结果。
* **目标角色**：平台管理员；销售组长和普通用户无入口且写 API 返回 403。
* **入口与 URL**：从 `/admin/users` 的“批量开户”进入独立可恢复页面；batch_id、当前步骤、筛选和错误定位写入 URL 或稳定路由状态。
* **页面模型**：Command–Execution + Process，不使用长表单 Modal；每个阶段只有一个主操作。
* **信息优先级**：当前批次/阶段与范围 → 阻塞错误和影响 → 当前阶段主操作 → 行/团队明细 → 格式说明与审计引用。
* **主操作**：上传阶段“校验开户文件”；预览阶段“确认创建 N 个账号”；结果阶段“保存一次性账号凭据”。按钮必须写明对象和结果。
* **次级操作**：下载模板、下载错误报告、取消批次、仅重试失败团队、批量重置不可恢复凭据。
* **表格与筛选**：按团队/状态/错误类型筛选，支持姓名和邮箱搜索；第一列为行身份，错误精确到字段，服务端分页/排序适配大批次。
* **状态**：zero state、parsing、validating、waiting_for_input、ready、processing、partial_success、failed、cancelled、expired、stale/conflict、credential_lost、completed。
* **恢复**：刷新恢复批次和已填写映射；响应丢失不重复写入；凭据丢失明确告知不可找回并提供批量重置。
* **响应式**：桌面采用团队分组表格；窄屏保留阶段、错误摘要和逐行详情，复杂字段编辑转独立区块/Drawer，不横向压缩完整桌面表格。
* **性能与规模**：至少验证 50、500 和极端长文本行；长任务有稳定 batch URL、阶段、数量和结果位置，不要求用户盯住 Spinner。
* **埋点/审计**：记录模板下载、校验、确认、取消、部分成功、重试、凭据导出和重置；只记录数量、范围和对象引用，不记录明文密码或文件内容。

### 销售组长团队洞察

* **页面任务**：当销售组长跟进团队训练时，帮助其识别进度变化和需要关注的成员，理解原因并下钻查看事实记录。
* **核心对象**：授权 Team、TeamMembership、新人训练路径、管理员额外任务、训练结果、确定性风险分组、成员时间线。
* **目标角色**：`training_manager`；主组长与代理组长本期均为只读，平台管理员保留独立全局管理入口。
* **入口与 URL**：`/team` 为 Dashboard–Drilldown 概览，`/team/{learnerId}` 为成员详情；team、period、date_from/date_to、搜索和状态筛选写入 URL。
* **页面模型**：Dashboard–Drilldown；不是 KPI 卡集合。概览回答当前范围是否正常、什么发生变化、原因和下钻对象。
* **信息优先级**：授权范围/时间/数据更新时间 → 需要关注的风险分组 → 新人路径进度 → 额外任务进度 → 主要薄弱项 → 完整成员列表。
* **主要交互**：选择团队/周期、打开风险分组、进入成员详情；本期没有任务发布、管理或审核主按钮。
* **指标口径**：每个百分比显示分母和定义；当前/对比周期、发布通过标准、更新时间和筛选范围可见；零值、空值、未采集分别表达。
* **风险表达**：不做个人排名；按逾期/停滞、未达发布标准和主要薄弱项分组，说明规则、人数、趋势和命中原因，同一成员可命中多组。
* **成员列表**：结构化表格/列表支持姓名或邮箱搜索、路径状态和任务状态筛选；状态不是颜色唯一表达，行链接使用真实 URL。
* **状态**：loading/skeleton、无团队授权、团队暂无成员、当前筛选无结果、部分数据陈旧、接口失败/重试、无权限、授权已撤销、数据口径不可用。
* **响应式**：桌面保留比较密度；移动端按风险 → 两套进度 → 成员顺序纵向编排，表格保留关键列并用独立成员详情承载其余信息。
* **性能与新鲜度**：正常网络首个有意义结论目标不高于 1.5 秒；API 超过 500ms 进入性能告警观察，页面明确显示数据更新时间和刷新状态。
* **埋点/审计**：记录范围/周期切换、风险下钻、成员详情打开和读取失败；不将普通只读浏览写成高风险审计，不记录敏感训练原文。
* **AI 决策**：本期不用 AI 生成洞察；规则、SQL、统计和确定性分组足以完成任务。
