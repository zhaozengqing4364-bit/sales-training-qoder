# Design Artifact Audit Guide

> **Purpose**: 写完 prd/design/implement 产物后、`task.py start` 前，主动跑这套审计，找出"在某层做假设但没追到下游验证"的问题。不需要用户提醒"再审计一下"。

## 为什么需要这个指南

设计产物的 bug 多数不是逻辑错，而是**"仿现有 X 却没核实 X 真实结构"**、**"在 A 层做假设没追到 B 层验证一致性"**。这类 bug 在实现时才炸（编译失败/连接池耗尽/类型不匹配），修复成本远高于 design 阶段。

四轮审计经验：每轮换一个维度，就能挖出上一轮的盲区。单轮不够，复杂产物需要多维度交叉审。

## 审计触发时机

- 写完 prd.md / design.md / implement.md 任一产物后
- 产物送审用户前
- 修复一轮审计问题后（修复可能引入新矛盾，需再审）
- 任何"仿现有 X""走现有 Y""config.Z"的引用出现时

## 七维审计清单

每条都要**实际读代码核实**，不能凭记忆/印象。用 codegraph/grep/Read 追到定义。

### 维度 1：参照对象真实性（"仿现有 X" 核实）

每处"仿现有 X 模式""参照 Y 实现"都要核实：
- [ ] X **真的存在**吗？（不是凭印象以为有）
- [ ] X **真是那个模式**吗？（如"双实现"——核实是否真有双实现，还是只有单实现）
- [ ] X 的**真实落点**对吗？（接口在 domain？实现在哪个包？）
- [ ] X 的**真实数量**对吗？（如"10 个模板"——实际数一遍，别 grep 错）

**教训**：第一轮"仿 customerDetail/projectDetail 双实现"——实际它们也是内存实现，无独立 repository，不可作参照。

### 维度 2：包依赖方向（跨包引用核实）

monorepo 里每个"在 A 包用 B 包符号"都要核实：
- [ ] A 的 `package.json` **依赖** B 吗？（不依赖则 import 编译失败）
- [ ] 方向**不反转**吗？（避免 A→B 又 B→A 循环）
- [ ] 同进程性：A 和 B **在同一进程**跑吗？（worker adapter 给 api 同步用——落点应在 api，不是 worker）

**教训**：第二轮"Tavily adapter 放 worker"——api 不依赖 worker 包，且 api 同步调不能跨进程用 worker adapter。

### 维度 3：类型字段完整性（"config.Z" 核实）

每处 `config.X`/`providerConfig.Y`/对象字段引用都要核实：
- [ ] 该字段在**类型定义里存在**吗？（追到 type/interface 定义）
- [ ] 字段是**新加的还是已有的**？新加的要同步改类型 + 读取逻辑 + 守卫
- [ ] 两个对齐类型字段**一一对应**吗？（新建类型 vs 既有入参类型，字段对得上吗？多/缺字段？）

**教训**：第三轮 `providerConfig.retrieval`——ProviderConfig 类型只有 storage/transcription/ai，无 retrieval。第四轮 `PublicInfoSource` vs `VisitPreparationPublicSourceSummary` 字段不对齐（多 url/publishedAt）。

### 维度 4：事务与 IO 边界

涉及 DB 写 + 外部调用的流程要核实：
- [ ] **慢速外部 IO（网络检索 2-4s）不在 DB 事务内**——否则连接池耗尽
- [ ] 事务边界：哪步在事务内、哪步在事务外，**显式写清**
- [ ] 事务内只做**快写**，不做检索/HTTP/长计算
- [ ] 现有 `runXxx`/`runInTransaction` 包裹器**是否包整个操作**？若是，新流程能否整体放进去？

**教训**：第三轮 generate 检索放进 `runMobileRead`（= `db.transaction`）——2-4s 网络检索占用 DB 连接。

### 维度 5：调用方语义一致性（数据流 vs 现有架构 vs PRD）

数据流图的每一步都要对照现有代码确认调用关系：
- [ ] 数据流里某接口的**职责**和现有架构一致吗？（如 generate 是否自动存库？）
- [ ] 和 PRD 的**业务语义**一致吗？（如"保存"是销售主动动作还是自动？）
- [ ] generate/save/getCurrent 等**接口边界**清晰吗？（谁存、谁读、谁不存）

**教训**：第四轮数据流写"generate → repository.save"——但现有架构 generate 不存库、save 是独立接口，PRD 也说保存是销售主动动作。三处矛盾。

### 维度 6：测试即时影响（改签名的连带）

任何"改 sync→async""加注入参数""改返回类型"都要核实：
- [ ] 现有测试**调用点**会受影响吗？（改 async 后调用方需 await）
- [ ] 现有测试的**构造方式**还成立吗？（如 `buildApiApp` 不注入新依赖 → 测试调真实外部服务失败）
- [ ] 改动切片的**验证命令**会因现有测试红而失败吗？若是，该切片必须同步修测试

**教训**：第四轮 generate 改 async + 注入 provider——现有 3 个 generate 测试用 `buildApiApp` 不注入 provider，会调真实 Tavily 失败，切片5 验证过不了。

### 维度 7：产物内部一致性

三产物（prd/design/implement）+ research 之间：
- [ ] 同一事实在多处描述**一致**吗？（如"cURL 通过"——prd 勾了，implement 前置清单也要勾）
- [ ] design 的接口契约 vs implement 的步骤**对得上**吗？（契约写了 FromConfig，implement 切片有没有造它？）
- [ ] 字段名/术语**统一**吗？（如 summary vs snippet 混用）
- [ ] 验收标准**可测**吗？（每条能对应到具体测试/命令）

**教训**：第二轮 design 数据流用 `snippet`、接口契约用 `summary`——不一致。第三轮 implement 前置清单与 prd 状态不一致。

## 审计执行方法

1. **重读产物全文**——不凭记忆审，对着文件审。
2. **每个"仿/参照/走现有/config.X"追到定义**——codegraph/grep/Read 核实。
3. **数据流图逐步对照现有代码**——每一步的调用关系、职责、事务边界核实。
4. **跨文件字段对齐**——新建类型 vs 既有入参类型，逐字段比对。
5. **修复后必须再审**——修复可能引入新矛盾（如第四轮是前三轮修正暴露的下游问题）。
6. **多轮直到清零**——每轮换维度，挖不出新问题才算通过。

## 审计盲区规律（已沉淀）

| 轮次 | 盲区类型 | 表现 |
|---|---|---|
| 1 | 参照对象失实 | "仿双实现"但双实现不存在 |
| 2 | 包依赖 + 状态一致 | adapter 放错包；cURL 通过未回写 |
| 3 | 类型字段 + 事务边界 | ProviderConfig 无 retrieval；检索进事务 |
| 4 | 调用方语义 + 类型对齐 + 测试 | generate-save 矛盾；类型不对齐；测试即时红 |

规律：**在 A 层做假设时，必须追到 B 层（调用方/类型定义/测试/包依赖）验证一致性**。盲区永远在"假设与下游不一致"处。

## 何时停止审计

- 连续一轮换维度后**挖不出新问题** → 通过
- 挖出的问题都是 🟡 建议级（非 🔴 硬错误）→ 可送审，建议项标注
- 仍有 🔴 硬错误（编译/连接池/类型/语义矛盾）→ 必须修完再审

## 输出格式

每次审计输出结构化报告：
1. 总体结论（架构方向对不对、硬错误数）
2. 逐问题：🔴必须改 / 🟡应改 / 🟡建议，附核实证据 + 后果 + 正确做法 + 影响范围
3. 修复稳定性确认（前几轮修正有没有回退）
4. 修复清单（按优先级）
5. 元反思（本轮盲区规律，补进本指南）
