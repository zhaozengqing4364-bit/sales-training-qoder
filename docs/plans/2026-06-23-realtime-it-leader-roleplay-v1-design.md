# 15 分钟信息化负责人实时客户对练 v1 方案

## 1. 背景与目标

当前实时语音对练的核心问题不是单一模型能力不足，而是长流程角色扮演缺少工程约束：记忆容易漂移，客户角色边界不稳定，知识库没有按可见范围接入，评分结果如果只靠模型自由判断也不够可信。

v1 只验证一个高价值样板：销售新人和国企、央企、政教医的信息化负责人做 12-15 分钟首次拜访实时语音对练，训练重点是方案可信度和需求澄清。

本设计现在作为后续 v1 implementation scope 的实现依据，不再保留“当前不进入实现阶段，因此不修改代码”的约束。本次补丁只明确实施边界，不修改产品代码。

v1 的成功标准是：

- 15 分钟内语音对话基本流畅。
- AI 客户不明显角色漂移。
- AI 客户不泄露隐藏信息、评分规则和标准答案。
- 客户能围绕部署、性能、集成、现有系统边界、PoC 指标提出合理质疑。
- 结束后报告能给出分数、原话证据和下一次训练建议。
- 管理员能区分学员能力问题和 AI 角色质量问题。

## 2. 用户画像与训练场景

### 学员

销售新人或需要训练行业方案沟通能力的售前、销售人员。v1 不要求学员完成成交，只要求完成首次拜访中的可信沟通。

### AI 客户

AI 客户固定为国企、央企、政教医大型组织的信息化负责人，可能职位包括信息中心主任、信息化处负责人、数字化建设负责人。

客户性格是谨慎、务实、专业，不轻易认可新平台。客户关注系统稳定、安全合规、现有系统集成、部署方式、性能影响、审计价值和 PoC 可验证性。

### 管理者

销售负责人、培训负责人或新人培养负责人。管理者需要看到学员能力短板，也需要看到 AI 训练质量是否可靠。

## 3. 训练流程

v1 固定为首次拜访，产品范围固定为石犀数据流动治理平台。训练总时长建议 12-15 分钟，分为四个阶段：

| 阶段 | 时间 | 训练重点 |
| --- | --- | --- |
| 开场与来意 | 0-3 分钟 | 学员是否说明拜访目的，避免一上来推产品 |
| 现状澄清 | 3-7 分钟 | 是否询问系统、接口、数据流动、现有安全设备 |
| 方案可信度 | 7-12 分钟 | 是否回应部署、性能、集成、差异、误报、PoC |
| 下一步推进 | 12-15 分钟 | 是否提出调研、PoC、风险梳理、汇报材料路径 |

阶段推进采用半自动策略：默认按时间推进；如果学员缺少关键动作，客户继续追问；如果学员提前完成关键动作，客户提前加压。

四个阶段只作为本次 roleplay phase/view 使用，不新增 `SalesStageCapability` stage 枚举，也不引入第三套销售 stage。实现时应把阶段状态限制在本场对练运行态、报告投影或样板配置内。

## 3.1 入口轨道与实现边界

v1 入口选择平台直练 `/practice/[sessionId]`：

- 通过 `VoiceRuntimePolicyService` 生成或读取 `voice_policy_snapshot`。
- 通过平台现有 StepFun realtime 路径进入语音对练。
- 不接入 `sales_trainer` 新人训练路径中的 realtime 占位。
- 不通过 `PracticeTemplate` 课程闭环开练。

该选择用于避免同时引入新人训练路径、课程模板闭环和平台直练三套入口语义。v1 只验证固定样板的实时客户对练能力，后续是否纳入课程闭环应另行设计。

## 4. 角色合同

角色合同是一次训练运行时冻结的客户扮演边界。实时模型不从后台最新配置反复拼装角色，而是消费本次会话冻结后的合同。

角色合同包含：

```json
{
  "customer_role": "国企/央企/政教医信息化负责人",
  "scenario": "首次拜访",
  "training_goal": "方案可信度",
  "visible_knowledge": ["客户背景", "行业共性", "公开产品认知"],
  "hidden_knowledge": ["评分规则", "标准答案", "内部销售话术", "隐藏预算", "决策链"],
  "behavior_rules": ["谨慎", "专业", "多追问落地", "不主动帮学员"],
  "forbidden_behaviors": ["泄露答案", "扮演教练", "替学员总结需求"]
}
```

客户可以追问“和现有 API 网关有什么区别”“串行业务链路会不会影响稳定性”“PoC 看哪些指标”。客户不能提醒学员应该怎么答，也不能主动说出评分维度或标准答案。

每次会话必须冻结 `roleplay_contract`，并记录 `roleplay_contract_hash`、revision refs 和生成来源。runtime 禁止 fallback 到 latest assets；配置发布或回滚只影响未来会话，不改变已开始或已完成会话的合同。v1 入口必须可通过配置或 feature flag 关闭。

## 5. 会话状态卡

状态卡负责把 15 分钟长流程压缩成可控结构，避免实时模型依赖长上下文硬记。

状态卡建议包含：

```json
{
  "current_stage": "discovery",
  "customer_attitude": "谨慎但愿意继续听",
  "confirmed_facts": [],
  "learner_actions_done": [],
  "learner_actions_missing": [],
  "objections_raised": [],
  "hidden_info_revealed": [],
  "next_pressure": "追问和现有 API 网关的区别"
}
```

状态卡每 2-3 轮异步更新一次。实时热路径读取当前状态卡和最近几轮对话，不读取完整历史。

异步状态卡更新必须带 version 或 sequence。后到的旧版本更新应丢弃；更新失败时保留上一版状态卡，不清空 runtime 状态。客户端或 realtime 连接重连时，应从 persisted snapshot / runtime_state 恢复当前合同、阶段、状态卡和必要事实。

## 6. 知识库接入

知识库必须分层，不能把所有知识都给 AI 客户。

| 知识层 | 使用对象 | 内容 | 是否给 AI 客户 |
| --- | --- | --- | --- |
| 客户背景 KB | AI 客户 | 国企、央企、政教医的信息化背景、系统复杂度、合规压力 | 是 |
| 产品事实 KB | AI 客户和评分器 | 石犀平台定位、能力边界、常见部署和 PoC 事实 | 有限给 |
| 评分教练 KB | 评分器和管理员 | 评分规则、标准答案、销售动作清单、内部培训材料 | 否 |

知识检索不进入每一轮实时热路径。会话开始前预取产品事实、客户背景和常见异议；明确遇到产品事实问题时再触发有限检索。检索超时不能阻塞语音对话。

如果产品事实缺失或检索超时，AI 客户不得臆测石犀平台能力，应自然追问或表达“需要你们给出可验证材料/PoC 指标”。该类降级需要记录到 `quality_flags`，并累计 `knowledge_timeout_count`，供管理员质检和后续回归分析使用。

## 7. 实时语音架构

v1 架构按热路径、旁路和离线三层拆分：

```text
实时热路径：
StepFun Realtime
+ 最近几轮对话
+ 短角色锚点
+ 当前状态卡
+ 必要事实

旁路异步：
转写保存
状态卡更新
知识预取
角色漂移检查

离线：
评分
报告
复练对比
回归评测
```

StepFun Realtime 负责语音输入输出、自然接话和短期对话。角色边界、阶段、知识可见范围和评分不交给实时模型自由发挥。

每个阶段可通过短 `session.update` 注入阶段锚点，例如当前阶段、客户态度、下一轮追问方向和禁止事项。

最低观测字段：

| 字段 | 用途 |
| --- | --- |
| `roleplay_contract_hash` | 确认本次会话使用的冻结角色合同 |
| `state_card_version` | 排查状态卡乱序、失败和重连恢复 |
| `violation_count` | 统计角色漂移、教练化表达、隐藏信息泄露等违规次数 |
| `blocking_violation_count` | 标记需要阻断报告或人工复核的严重违规 |
| `knowledge_timeout_count` | 统计知识检索超时或缺失降级 |
| `scoring_confidence` | 标记评分置信度和人工复核需求 |
| `quality_flags` | 汇总 AI 角色质量、知识降级、评分异常等质量标记 |

## 8. 评分体系

评分采用“离线大模型评分 + 规则校验 + 原话证据”，不使用实时语音模型直接评分。

流程如下：

```text
完整转写
→ LLM 提取关键销售动作
→ 规则校验提取结果
→ LLM 按 rubric 评分
→ 规则校验报告一致性
→ 低置信度进入人工复核
```

大模型负责理解销售表达、归纳行为和生成建议；机器规则负责校验证据来源、分数加总、报告格式、缺失动作一致性和明显矛盾。每个分数必须绑定学员原话证据，没有证据的判断不展示给学员。

评分总分 100：

| 维度 | 分值 |
| --- | --- |
| 开场与来意 | 15 |
| 现状澄清 | 20 |
| 风险识别 | 20 |
| 价值说明 | 20 |
| 可信度回应 | 15 |
| 下一步推进 | 10 |

这 6 项 100 分 rubric 是 v1 的版本化 scoring ruleset / report projection。实现时不得破坏现有架构文档里的 5 个教练维度；如果现有 evaluation 层已经依赖 5 维结构，则保留映射说明：6 项用于本样板报告，5 维作为现有 evaluation 兼容层。

## 9. 报告视图

### 学员反馈视图

学员视图用于训练改进，避免做成审判书。

包含：

- 总分。
- 六项得分。
- 本次做得好的 3 个表现。
- 最需要改进的 3 个动作。
- 对应原话证据。
- 下一次训练建议。

### 管理员质检视图

管理员视图用于管理训练质量和新人能力短板。

包含：

- 学员、场景、时长、完成状态、总分、评分置信度。
- 六项拆分、扣分原因、原话证据。
- 缺失动作统计。
- AI 质量检查：角色漂移、隐藏信息泄露、教练化表达、上下文丢失、是否建议人工复核。
- 原始转写、评分 JSON、状态卡快照、角色合同 hash。

### 权限矩阵

默认 fail-closed；没有明确授权时不返回敏感训练材料。

| 角色 | 可见内容 |
| --- | --- |
| learner | 总分、六项分项、改进建议、绑定到学员原话的证据 |
| admin / supervisor | 完整转写、评分 JSON、状态卡、角色合同 hash、AI 质量检查、状态卡版本 |
| ops | 脱敏日志、指标、质量 flags、错误和耗时统计；不可看完整训练内容和评分细节 |

## 10. 验收指标

v1 验收不使用“像真人”这类模糊标准，使用可观察指标：

- 12-15 分钟对练不断线或可恢复。
- 首句响应稳定在 1-2 秒级，复杂知识问题允许更慢但不阻塞对话。
- AI 客户不明显忘记自己是信息化负责人。
- AI 客户不主动暴露隐藏信息、评分规则和标准答案。
- 学员泛泛讲产品时，AI 能追问和现有系统的关系。
- 学员过度承诺时，AI 能追问 PoC 指标或可验证性。
- 结束报告包含分数、扣分原因和原话证据。
- 同一段转写重复评分，分项得分差异保持在可接受范围内。
- 管理员能看到 AI 角色质量检查结果。

## 11. 回归样本结构

v1 至少准备 9 段评分回归样本结构，不需要在本设计里写完整 transcript。样本按质量分层：

| 层级 | 数量 | 目标 |
| --- | --- | --- |
| 优秀 | 3 段 | 覆盖主动澄清、克制承诺、能推进下一步的高质量表达 |
| 普通 | 3 段 | 覆盖部分动作完成、证据不足、推进不够清晰的中等表达 |
| 较差 | 3 段 | 覆盖跳过澄清、夸大能力、泄露诱导、无法推进的低质量表达 |

9 段样本合计必须覆盖：开场、现状澄清、风险识别、价值说明、可信度回应、下一步推进、隐藏信息防泄漏、知识缺失降级、评分证据绑定。

## 12. v1 暂不做

为保证样板可验证，v1 明确不做：

- 多行业、多客户角色自由配置。
- 长期客户关系记忆。
- 多轮拜访连续剧情。
- 实时教练打断。
- 模型微调。
- 复杂后台配置中心。
- 每轮强制知识库检索。
- 大量 UI 和运营配置扩展。

这些能力等单场景样板稳定后再进入 v2/v3。

## 13. 后续演进

| 阶段 | 方向 |
| --- | --- |
| v1 | 单场景验证：信息化负责人首访、15 分钟、角色稳定、知识可控、离线评分 |
| v2 | 增加复访、方案评审、采购/业务负责人等有限场景 |
| v3 | 多角色组织关系、长期客户关系史、跨多次拜访训练 |

当前最重要的产品判断是：先把一个样板练准，再扩展平台能力。
